# 长录运行统计与内存风险

## 本次范围

继续推进 M5 的运行稳定性，同时改善 M4 的设置交互。本次增加只读诊断，不改变
录像、RTSP 的资源归属或并发策略，不自动切段、不新增录像时长上限。
仍是单 Linux 业务进程，显示和触控的已通过参数保持不变；板端离线，未部署。

## 为什么要检查长录内存

帧队列有上限，不意味着整个录像过程内存有上限。选用 SDK 的 `mov-writer.c`
会为每个样本保留 `mov_sample_t` 索引，关闭文件前不释放；每次扩容增加 1024
个槽位。音频也占用索引，所以不分段长录可能持续增长。

本地 LCKFB defconfig 为 Linux 分配 128 MiB，但尚未核对板端实际 DTB 和可用内存。
本次不据此强加一个未经实板测量的停止阈值。设置页提醒长录启用分段，仍保留
用户选择“不分段”的能力；未实现内存临界自动保护，不能承诺不分段连续 8 小时。

## 日志内容

录像在启动、约每 10 秒、段关闭前和最终停止/启动失败输出统计；RTSP 在启动、
约每 10 秒、视频消费线程退出和停止输出统计。原逐 120/200 回调日志改为仅保留
前三次回调，减少刷屏。定时统计随 worker 执行，不是独立看门狗，不能中断 SDK
硬阻塞或保证阻塞期间仍有周期日志。

| 日志 | 主要字段 | 用途 |
| --- | --- | --- |
| `queue` | depth/bytes、peak_depth/peak_bytes、accepted/popped/discarded/rejected、oldest_us/max_residence_us、closed/error | 区分积压、溢出和正常停止丢弃 |
| `muxer` | segment、tracks、samples/capacity、index_bytes、media_bytes、stats_error | 查看当前段已分配样本索引，切段后是否回落 |
| `stats` | proc_valid、cpu_ticks/clk_tck、rss_kib/hwm_kib、fds、mem_available_kib | 观察 Linux 内存、CPU 累计时间和 FD 趋势 |
| 录像 `runtime` | state/error/stop、segments、video_frames、written_bytes、elapsed_ms、末视频/音频 PTS | 与业务状态和文件阶段关联 |
| RTSP `runtime` | stopping、video/audio_callback_attempts、video/audio_error | 查看源消费是否继续，不代表客户端收到 RTP |
| `first_frame_latency_ms` | worker 开始至首个 IDR 成功写入的单调时钟耗时、capture_pts_us | 区分启动等待与后续停流 |

`proc_valid` 按位说明：CPU=1、RSS=2、HWM=4、FD=8、MemAvailable=16；全部有效
为 `0x1f`。缺失字段的零值不能当作“没有内存占用”。CPU 使用时间可由两次
`cpu_ticks` 差除以 `clk_tck` 得到；它是整个 UI/媒体进程的累计 CPU 时间，
不是某个模块的独立使用率。HWM 是进程历史峰值，停止后不会下降。

队列计数满足 `accepted - popped - discarded == depth`，关闭或失败后保留统计，
下一次订阅重置。等待时间用本地 `steady_clock` 的入队时间计算，与摄像头 PTS
和手动 UTC 校时无关；`max_residence_us` 只统计成功出队的驻留时间。

`index_bytes` 是各轨道 `sample_capacity * sizeof(mov_sample_t)` 的总和，不含
allocator 开销、全部 muxer 缓冲、进程 RSS 或大核 VB。`media_bytes` 是写入
mdat 的媒体字节，不等于最终文件大小。多个队列可能引用同一不可变帧，不能
简单把各队列 bytes 相加当作实际物理内存。

## 实现边界

- 队列快照只持有自己的互斥锁；不调用 SDK、不逐帧写日志，仅增加入队时间和计数。
- `/proc` 采集不持有录像状态锁，不修改网络/时钟/媒体；解析 stat 时跳过最后一个
  `)` 以前的进程名称，检查 CPU 数字和溢出。FD 计数排除采集器自己打开的目录。
- MP4 新增 worker 专用 `lawrec_mp4_muxer_stats()`，只遍历轨道，不扫描样本数组或
  执行 I/O；可以在已有 I/O 故障后读统计，不清除原错误。段关闭前先记录索引。
- 延续四份 SDK 源码指纹和项目输出目录生成方式，未修改 SDK 原文件。SDK 视频
  track 延迟至首个有效码流创建，首帧前 tracks=0 属于当前实现的正常状态。
- 当前尚无共享 VENC/AI 硬件状态快照；队列关闭和 FD 稳定都不能证明大核资源已经
  释放。真实音画同步、码流和停止后资源回收仍需上板确认。

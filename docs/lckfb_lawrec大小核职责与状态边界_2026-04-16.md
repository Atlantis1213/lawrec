# lckfb lawrec 大小核职责与状态边界

## 1. 目的

本文档用于落实收敛清单中的 `P0-5`：

- 明确 `lawrec` 当前大小核职责边界
- 明确当前主线需要遵守的状态边界
- 为后续 RTSP、录像、拍摄业务提供统一约束

## 2. 当前推荐职责划分

### 小核 Linux 负责

- UI 页面
- 输入事件
- 页面切换
- 状态展示
- 与大核的 IPC 控制
- RTSP server
- 业务状态机与控制逻辑
- 小核单进程主应用内部模块调度

### 大核 RT-Smart 负责

- 摄像头采集
- 显示底层 owner
- 预览图层控制
- VENC 编码
- AI 推理
- 被动执行 IPC 命令

## 3. 当前明确不建议的职责漂移

当前阶段不建议：

- 让小核接管摄像头主数据面
- 让小核直接承担视频编码主链
- 让大核直接承担复杂 UI 流程
- 把 RTSP、录像、AI 继续直接堆进 `main.cc`

## 4. 当前状态边界

### 预览状态

- `preview backend ready`
  - 表示显示底座、摄像头和空白帧资源已完成初始化
- `preview enabled`
  - 表示当前允许把摄像头预览绑定到显示图层

### AI 状态

- `ai pipeline enabled`
  - 表示允许实时跑 `retinaface/mobile_face`
- 当前默认应视为可选能力，不再作为开机主线强依赖

### 兼容残留状态

- `legacy face db enabled`
  - 表示历史人脸库共享内存和识别链仍可使用
- `legacy import path active`
  - 表示 `/sharefs/pic/` 导入流程仍保留

这两条都不属于 `lawrec` 当前主线，只是兼容保留。

## 5. 后续功能必须遵守的规则

### RTSP

- RTSP 的视频数据 owner 仍在大核编码侧
- RTSP server owner 在小核
- 小核不只是“控制和展示状态”，还负责 RTSP 协议服务与会话管理
- 大核只负责为小核 RTSP 提供可消费的编码能力，不负责监听 RTSP socket

### 录像

- 录像应与预览分离为独立状态
- 不要让“进入拍摄”天然等于“开始录像”

### AI

- AI 是否开启必须是显式状态
- 不允许再依赖“只要开预览就一定跑 AI”

## 6. 当前结论

当前 `lawrec` 的系统底座应理解为：

- 小核是“控制面 + RTSP 服务面”
- 大核是“媒体数据面”

后续任何新功能，只要违反这条边界，都需要先重新评估，而不是直接落代码。

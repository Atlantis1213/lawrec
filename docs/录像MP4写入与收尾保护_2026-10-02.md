# 录像 MP4 写入与收尾保护

## 发现的问题

本轮推进 C05/C08、S02/S03 与 R03 的录像失败处理。检查当前选用的 SDK 后发现：

- `kd_mp4_write_frame()` 忽略底层 `mp4_writer_write()` 返回值。
- 关闭接口忽略写入尾部索引、`fflush()` 和 `fclose()` 错误。
- 短写可能没有 `ferror()` 标志，旧回调仍报告成功。
- 创建文件或内部 writer 失败时，可能泄漏大约 4 MiB 的实例或留下无效 writer。
- 编码转换失败后，负长度可能继续传入 writer；内部转换缓冲实际为 2 MiB。

故障注入中进一步复现 fast-start 收尾 CPU 持续占用：错误状态下元数据大小为零，
SDK 搬移循环按零长度递增，无法退出。还发现短录像最后一次读取超出 EOF，
其结果实际不再使用。仅在应用外层检查旧 SDK 返回值不能覆盖这些问题。

## 当前实现

项目新增 `little/src/record/prepare_mp4.cmake`：在 Docker 构建目录生成选用 SDK
的 `mp4_format.c` 与 `mov-writer.c` 适配副本，不修改 SDK 源码，也不复制整套
封装库到业务源码树。两份 SDK 输入使用 SHA256 固定，并逐段核验替换位置；
SDK 升级不匹配时明确失败，需要复核适配与真实 SDK 测试，不能只更新哈希绕过。

适配副本参与 UI 可执行文件链接，替代静态库中的对应对象，其余格式实现继续
复用 SDK。保留正常 MP4 和 fast-start 功能，没有改成不含索引的简化输出。

| 保护 | 行为 |
| --- | --- |
| 写入、读取、定位失败 | 每个 muxer 独立记录第一次 I/O 错误，不被后续成功操作清掉 |
| SDK writer 返回值 | 视频/音频四条写入分支均传回失败 |
| 延迟的缓冲写入错误 | 录像 worker 原有 100 ms 空间检查节点先刷新 stdio 并检查错误 |
| 文件收尾 | I/O 失败跳过继续搬移，但释放轨道、writer 和文件；关闭错误传回调用方 |
| fast-start 搬移 | 零长度/异常长度拒绝；搬移读写失败退出；末尾不执行无用的越界读取 |
| 初始化失败 | 清空输出句柄，关闭已打开文件并释放实例及部分 writer |
| 长度保护 | 输入超过 2 MiB 或转换结果无效时明确失败，不把负长度传入 writer |
| 文件发布 | 写入、刷新、收尾失败时保留 `.part`，不发布为完成的 `.mp4` |
| 原始错误 | 清理错误另行打印，不覆盖首次写盘错误，如 `-ENOSPC` |

录像 worker 是唯一 MP4 写入/刷新/关闭者。SDK 音视频回调仍只向有界队列复制数据，
编码器和媒体租约管理不变。RTSP 及已通过的显示/触控配置未改。

同时删除录像模块内已经不用的 mkdir、旧命名函数、`/tmp` 回退和媒体状态字段。
保存目录与命名统一由 storage/settings 管理；不自动建目录。启动前确认 H.264
后，异步 worker 不再解引用调用方的类型/目录/前缀字符串，消除旧路径的生命周期风险。
`lawrec_record_config_t` 的历史字段保留布局，但不再作为独立的存储配置入口。

## 验证证据

```bash
bash tools/test.sh record-io
bash tools/build.sh little
```

均通过 Docker。定向测试使用当前 SDK 真实格式引擎，不用模拟 MP4 API 代替：

- 正常 H.264 文件和 G.711A 音轨可由 SDK 读回，核验样本、音频类型与时间戳。
- 80 帧多块 fast-start 搬移后，逐帧字节与时间戳一致；同时覆盖很短的录像。
- 注入写入、无 errno 的短写、读、seek、tell、flush、close 故障；返回错误且收尾退出。
- `/dev/full` 实际返回 ENOSPC，补充不依赖 mock 返回值的延迟写失败证据。
- 两个 muxer 的错误互不污染；超限输入明确拒绝。
- 十次文件打开失败、两级 writer 分配失败及初始化写失败，核验实例释放与句柄清空。
- 应用分段测试继续检查 IDR/SPS/PPS 起点、音视频 PTS、失败段不发布，以及首个错误保留。

故障注入只在测试可执行文件中包装 libc 调用，生产程序不使用这些全局包装。
测试设 10 秒报警，防止新的 SDK 收尾循环让验证进程无限挂住。
日志：`out/record-io-tests.log`、`out/record-io-build.log`；最终测试及目标构建未见警告。
目标构建与 native 测试使用的两份适配 C 文件已逐字节核对一致。
Docker 中对安装到 target 的 UI 检查符号表，确认存在刷新、受保护收尾及
`kd_mp4_write_frame` 实现；不是只生成副本而仍链接旧接口。

## 运行定位与剩余工作

重点查以下日志及错误码，不只看“录像停止”按钮：

```text
[lawrec-record] video write failed last_error=-28 path=...part
[lawrec-record] MP4 flush failed last_error=-28 path=...part
[lawrec-record] MP4 finalize failed last_error=... path=...part
```

`-28` 为 ENOSPC，`-30` 为 EROFS，`-5` 为 EIO；失败文件不进入完成文件列表。
成功的早期分段保持已发布状态，最后失败段单独保留供定位，不能承诺自动恢复。

本轮未上板、未生成新 SD 镜像。实际 SD 满盘/只读、真实编码文件的 VLC 解码、
音视频同步、2h/8h 长测仍待验收。测试码流是容器样本，不是可播放画面的实测。
刷新 stdio 不等于 fsync/断电恢复；底层文件系统调用阻塞没有硬超时保证。
SDK 封装器仍不是任意恶意码流的安全沙箱；音频停止尾帧与跨分段迟到数据的完整
同步处理仍需继续完善，不把本轮写盘保护当作全部媒体验收通过。

从旧整卡镜像更新时须同时带上此前设置/映射增量的 UI、`liblvgl.so`、
`liblv_drivers.so` 和同版本 `S45wifi`；本轮 MP4 适配实现直接在 UI 程序内。

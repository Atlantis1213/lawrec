# 预览退出与 IPC 恢复

## 本轮解决的问题

| 场景 | 原风险 | 当前处理 |
| --- | --- | --- |
| 进入预览尚未回包就点击返回 | EXIT 被 pending ENTER 拒绝，进入成功后没有继续退出 | UI 每次轮询检查返回意图，先等进入结果，再等待 RTSP/录像停止，发送一次 EXIT |
| 结果队列已满时请求超时 | 超时仍投递到同一队列，可能持续丢失，pending 无法清除 | UI 线程直接完成超时处理，不依赖队列容量 |
| EXIT 返回失败或没有回包 | 小核清空预览标记，回放可能占用尚未释放的显示层 | 停止依赖媒体并保留预览占用；只有收到匹配的 EXIT 成功才能解除保护 |
| 两次 UI 轮询间断线并重连 | IPC 状态又变成 connected，旧成功回包可能恢复预览状态 | 连接代次变化撤销旧请求；既有序号检查继续拒绝迟到结果 |
| 请求发送与断开同时发生 | 检查过的原子 handle 不能保证发送时仍属于同一连接 | SDK 发送、同步显示请求及断开通过同一传输锁固定 handle 生命周期 |

这里的“预览已就绪”仅表示大核 ENTER 命令成功，不代表已经收到摄像头帧。
没有新增线程、服务或 IPC 协议，也没有修改大核、触控驱动或显示参数。

## 状态约束

```text
ENTER 请求 -> 预览占用，媒体尚不可启动
ENTER 成功 -> 允许用户启动 RTSP / 录像
返回意图 -> 等待进入结果及两个媒体消费者停止
EXIT 请求 -> 媒体不可启动，回放仍被阻止
EXIT 成功 -> 清除预览占用，返回主页面
失败 / 超时 / 断线 -> 保留占用，禁用媒体；用户重试返回
```

EXIT 不无限重试；失败后取消返回等待，保留失败提示和返回按钮。断线后也不
自动重新开启摄像头、推流或录像。即使尚未成功发送 ENTER，也保守要求一次
成功 EXIT 来确认大核状态，不把连接失败推断成后台空闲。

日志包含请求命令、序号、连接代次、结果；接收端保留完整的大核错误值，错误
消息长度及协议版本有明确拒绝日志。预览关闭未确认时，控制层回放返回 EBUSY。

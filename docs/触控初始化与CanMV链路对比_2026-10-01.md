# 触控初始化与 CanMV 链路对比

## 结论与边界

当前优先检查显示工作状态下的触控初始化、ST7701 板级配置和触点协议，
不继续通过坐标映射或滤波掩盖原始事件异常。尚未证明唯一根因，也未修复验收。
这里讨论的是 MIPI DSI/PHY 和 VO 像素时钟；MAPI 是软件接口层，不是时钟。

用户实测：启动 UI 前点击正常，启动后 evtest 异常，停止后仍偶发异常。
这排除了“仅 LVGL 把坐标映射错”作为完整解释，但不证明 UI 一定改了时钟。
显示内容、扫描时序、供电和干扰变化，都可能在时钟频率不变时影响触控。

## 与本工程的差异

### 1. 初始化先后与 RESET

本工程：Linux 启动时 probe 触控；大核手动启动后初始化 connector/DSI/VO；
小核 UI 依次初始化 DRM、evdev、页面、按键和 IPC。两核之间没有在这条
初始化路径上保证“显示稳定后才初始化触控”的屏障。

Linux `edt-ft5x06.c` 未注册 `input->open/close` 回调，IRQ 在 probe 时申请。
所以 UI 再次 open evdev 不会重新执行 probe 或 RESET；不能把官方构造函数
等价为 Linux `open()`，也不能通过交换 UI 中两个 init 调用就复现官方复位。

复位时序需纠正：

- Linux 请求 RESET 时为逻辑 1，等待 5~6 ms，置逻辑 0，再等待 **300 ms**。
  当前低有效配置对应物理低后高，不是只有数毫秒的启动等待。
- 官方 CST128 reset 使用 `1-rst_valid` 20 ms、`rst_valid` 10 ms、
  `1-rst_valid` 50 ms。已查庐山派 defconfig 未覆盖 Kconfig 默认有效值 0，
  按这些默认值应是物理 **高 20 ms、低 10 ms、高 50 ms**，不是低高低。
- 官方 probe 另有 50 ms 等待，线程化 reset 路径另有 30 ms 等待。
  不应把这些分属不同阶段的延时简单描述为一个固定波形。
- 以上是源码推导，不是板端波形测量。不要由应用直接抢占内核 GPIO 来复位。

### 2. 显示时序与时钟

| 项目 | 本地 SDK ST7701 表/初始化 | 新版官方 LCKFB 专用配置 |
| --- | --- | --- |
| 配置像素时钟 | 39600 kHz | 27561 kHz |
| H active/sync/back/front | 480 / 20 / 20 / 80 | 480 / 8 / 10 / 30 |
| V active/sync/back/front | 800 / 10 / 70 / 220 | 800 / 10 / 20 / 40 |
| 配置时钟及 totals 推算帧率 | 60 Hz | 约 60 Hz |
| page 0x10 的 C1 | 10 02 | 04 02 |
| page 0x10 的 C2 | 31 02 | 37 08 |
| page 0x10 的 CC | 10 | 38 |

这些是配置值，不是实测频率；旧枚举名带 30FPS 也不能当作真实刷新率。
Gamma、供电/GIP 和其它初始化命令也存在差异，不能只替换表中三个寄存器。

真正的旧 SDK 硬件入口在大核：
`sample_connector_init -> kd_mpi_connector_init -> st7701_init`，后者设置
`pixclk_div=14`、PHY、DSI、面板命令和 VO。`connector_set_pixclk` 下接
`k230_set_pixclk`，本地链接在 `libvo.a`，不能仅依据表中数字宣称已确认 PLL。
PHY 表与结构体对应为 n=9、m=196、voc=0x17、hs_freq=0xa3。

小核确实提交 connector CRTC_ID、MODE_ID、ACTIVE 和 plane 配置，但本地
Linux `canaan_vo_enable_crtc/disable_crtc` 是空实现，DSI DCS 写函数也是
占位实现。因此不能直接推断 Linux 1080x1920 DRM 模式重编程了物理 MIPI。
它仍会修改 OSD/VO 图层并写配置加载寄存器，显示内容变化并不等于时钟变化。

### 3. 协议差异

当前 GENERIC_FT 路径从 0x00 读取，跳过三字节头，遍历全部五个记录，
依赖记录中的 event/id 释放槽，不使用 0x02 数量限制解析，也未丢弃越界坐标。
官方 CST128 按数量解析并合成释放。如果 IC 没有提供兼容 FT 的无效槽/UP，
Linux 就可能留下活动槽。但未抓到 I2C 原始包前，这仍是待证假设。

不要全局把通用 FT 驱动改为只遍历数量：真正 FT 控制器的 UP 记录可能需要
独立处理。应在确认芯片/协议后使用板型专用 compatible/quirk，并完整处理释放。

### 4. 已发现的显示健壮性风险

- 大核忽略 `kd_mpi_connector_power_set/init` 返回值，上层也忽略 connector
  初始化结果；VO 线程创建/结果未完整检查，不能用 backend ready 日志证明显示已好。
- 小核 `drm_wait_vsync()` 无超时；`disp_flush()` 取不到空闲缓冲会一直循环。
  没有 vblank 时可阻塞 LVGL 主循环，导致不处理触摸/退出。这能解释部分 UI
  无响应，但不能解释内核为什么生成鬼触，必须分开处理。
- 小核 plane_config 失败仍设置 configured，显示线程创建结果也未检查。
  应补失败传播和有限等待，不应在没有成功翻页时直接重用扫描中的缓冲区。

## 下一轮最小执行顺序

1. 对齐用户正常工作的 CanMV 固件版本，确认其 LCKFB 专用 panel 和 CST128 配置。
2. 确认大核显示已就绪；分别比较大核背景、UI 禁触摸、UI 正常三组原始事件。
   必须记录是否有真实接触，不能用事件数量单独认定鬼触。
3. 若禁触摸 UI 也异常，优先对齐整套 panel/PHY/时序；同时检查显示稳定后
   由驱动管理的一次复位是否改善。两项分开 A/B，不把每次 open 自动复位作为补丁。
4. 若寄存器数量为零仍有 Linux 活动槽，实施 CST128 专用解析及释放；读取应在
   驱动内限频取样，不能用 i2cget -f 与正在工作的驱动争用总线。
5. 独立修复 connector 失败传播和 DRM 等待诊断；不要把它们宣称为鬼触修复。

若修改 connector 的内核初始化序列，必须更新大核 RT-Smart 固件；只 SCP ELF
不够。若修改 Linux 触控驱动，需要更新内核。所有构建仍只允许 Docker，
本轮只有源码核对和 shell 工具语法/板端采样验证，没有编译或烧录新固件。

## 用户补充资料复核

已参考用户提供的 CST128 调用链分析，保留以下区分，避免据此引入多余改造：

| 补充观点 | 核对结果与执行含义 |
| --- | --- |
| 官方 CST128 按数量解析，重新生成事件 | 与源码一致；重点验证 Linux 活动槽是否在数量归零后仍残留 |
| 官方 IRQ 不直接读 I2C | 线程化配置下成立；Linux 同样使用 `devm_request_threaded_irq(NULL, edt_ft5x06_ts_isr, IRQF_ONESHOT...)`，I2C 读取也不在硬中断上下文，无需再套一层线程 |
| 官方队列满时丢旧数据 | 成立；Linux evdev 溢出也丢弃未消费事件并插入 `SYN_DROPPED`，不是无限保留旧事件，但两种机制并不等价 |
| 实际芯片一定为 CST128 | 板级配置支持该判断，但配置还启用了 GT911；设备名、480x800 范围都不是芯片身份证明，仍需版本/硬件或驱动内芯片读数佐证 |
| 当前最新正式版为 v1.8 | 资料的版本引用占位符无法核验，不能将开发分支代码当作 v1.8 发布镜像的确定实现 |

还需注意：官方 CST128 当前用记录索引作为 track_id，不是直接采用 FT 数据
中的硬件 ID；多指重排的语义也有差别。若移植 Linux 专用解析，必须定义完整的
槽位生命周期，不能只抄坐标位运算。Linux 已声明范围为 0..479、0..799，
合法性检查应遵循实际 input 范围，不能原样照搬官方 `>480 / >800` 的边界。

Linux evdev 的队列属于各自打开的客户端：UI 消费慢不等于 evtest 必然消费慢。
两个读取器同时看到异常，更应比较驱动原始包和 input 状态，而非简单清空 UI 队列。
清队列不能修复持续错误的硬件触点，也可能吞掉正常短按或释放。

后续判断以同一包的 `数量 / 原始记录 / Linux 活动槽` 为准：

- 数量为零但活动槽未释放：优先修 CST128 协议适配。
- 数量合法但未接触仍持续产生触点：数量过滤不足以解决，继续显示/复位/干扰对照。
- evdev 正常而 UI 不响应：转查 DRM 阻塞及应用输入消费，不改触控硬件参数。

本次复核没有更换驱动、照搬队列或修改 MIPI 时钟。

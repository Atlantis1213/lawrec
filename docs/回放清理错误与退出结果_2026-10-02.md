# 回放清理错误与退出结果

## 本轮修复

回放的正常启动/读取错误与资源清理错误分开保留。状态新增 `cleanup_error`：
主错误保留首次播放失败，清理错误保留首次解绑/停止/销毁/释放失败；每个 SDK
原始失败仍打印。SDK 正数错误标准化为负数 EIO，合法非负 VB pool id 不变。

`stop_wait` 在 worker 已退出但硬件资源仍被隔离保留时返回清理错误，而非 0。
文件/解码错误之后若清理成功，仍可返回 0；不把历史文件错误误报为停止失败。
映射解除与文件关闭也检查返回值，继续保留 SDK stop 在 worker 中执行的顺序。

小核退出日志同时打印 playback/record/rtsp 的等待结果和保留的媒体 owner mask。
任一等待失败或 owner 仍存在，都以非零结果退出，不再漏掉回放和资源保留。
这不是强制释放大核硬件；进程退出不证明远端 codec/VB 已回收。

媒体头文件已支持 C/C++ 同一 ABI，C 入口直接读取原有 owner mask，不新增另
一份状态或服务。目标构建及共享媒体定向测试核对了使用关系。

## 界面与恢复边界

回放页在保留资源时显示首次清理错误；播放与清理不同原因时分别显示。
文件页继续禁止再次播放/删除，但不再暗示“只重启 UI 就一定能回收硬件”。
提示用串口检查与恢复，显示恢复功能不等于媒体回收。无法确认 codec/VB
是否回收时，应按已有文档完整重启后验收，不自动复位硬件或重启设备。

实际 LVGL [错误提示](../out/ui-preview/current/playback-retained.png) 已查看，文字
完整、按钮无重叠，y=200..469 视频区域仍不覆盖。后台为 fixture，不是板测。

## 定向验证

Docker `playback` 通过，实际生产 worker/解析辅助进程配 SDK mocks：

- 启动绑定返回正数 17 后，状态为失败且错误为 EIO，资源正常释放。
- 解绑 EPIPE 后销毁再返回 17，保留 EPIPE；资源/租约隔离，禁止再次启动。
- 送流 EBADMSG 后清理 EPIPE，分别保留两个原因，`stop_wait` 返回清理原因。
- pool 销毁正数错误后不继续释放其他池/租约，明确返回清理错误。
- 原有播放结束、暂停/停止、G711 短包和解析故障恢复场景继续通过。

隔离是进程生命周期策略，三个清理失败场景在独立测试进程中执行，测试不
直接清掉生产 poisoned 标记假装恢复。修复前正数错误断言记录为
`out/playback-cleanup-before.log`；重跑目录已用 mktemp，不再与旧 PID 目录冲突。

共享媒体 `media-lifecycle`、字库、生产 LVGL 渲染/交互和小核 Docker 构建通过。
日志为 `out/playback-cleanup-{tests,media,fonts,ui,build}.log`；未见编译器警告，
保留原 CMake 提示。最终退出日志的汇总路径由目标构建核对，未实际启动 UI
退出或注入真实硬件故障，不能说已测板端进程退出与资源释放。

大核/触控/显示参数保持不变，未部署或更新 SD 镜像。本轮准备生成开发快照，
成功与否及名称/哈希以 `out/releases/` 的实际校验后打包输出为准；默认正式
RC 的干净提交与全部测试门槛不变。快照只跑打包完整性与双核构建，不继承
完整功能验收结论。

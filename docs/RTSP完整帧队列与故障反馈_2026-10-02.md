# RTSP 完整帧队列与故障反馈

本轮收尾 M1 的首帧判断、有限队列和错误反馈。不修改触控、显示、大核或
编码参数；设置界面仍沿用已查看的最新 LVGL 图库。

## 问题与处理

| 问题 | 修复 |
| --- | --- |
| 编码器允许 4 MiB 帧，RTSP 源却静默丢弃超过 512 KiB 的输入 | 与编码帧上限对齐，超限/非法输入明确返回错误，不计成有效首帧 |
| 队列按 8 个 NAL 限制，多切片 IDR 入队一半便被清空 | 改为 8 个完整编码帧的队列，每帧 NAL 列表一次入队 |
| 拥塞清空后可能继续发送依赖旧帧的 P 帧 | 清空剩余旧帧并等待新 IDR，恢复从 SPS/PPS 和完整关键帧开始 |
| 多个 NAL 共享大缓冲区，只计剩余 NAL 会低估内存 | 整帧最后一个 NAL 离队之前，保留该帧全部 backing-buffer 字节记账 |
| 音频超时、解析失败等统一变成 EOVERFLOW | 从源/消费者返回具体错误，不把超时、ENOMEM、ENOBUFS、EMSGSIZE 混为一种 |
| RTP 缓冲区过小导致 NAL 截断 | 视频 sink/fragmenter 上限匹配编码帧；源收到过小读缓冲时明确关闭，不发送截断数据 |
| 创建会话中途失败留下已创建源或读帧线程 | 部分源/replicator 也进入清理，构造异常关闭已创建环境；子会话用局部 RAII 保护 |

首帧计数现在来自解析成功并整帧入队的 source，而非调用回调前递增的次数。
这证明内部源已准备，不证明有客户端，更不证明 RTP 送达或 VLC 解码成功。

## 上限与行为

- 单次编码输入最多 4 MiB；H264 每帧最多 128 个输入 NAL，SPS/PPS 单个最多 32 KiB。
- 原始队列最多 32 项且 8 MiB；完整帧队列最多 8 项且 8 MiB，两项限制同时生效。
- 解析队列拥塞时丢弃并等待 IDR；原始队列超限、音频拥塞、解析/分配错误终止本次推流并反馈。
- 不自动重启推流，不影响录像消费者，不改共享 VENC/音频的所有权规则。
- 视频 RTP 缓冲和 fragmenter 使用 4 MiB 上限；G711 sink 临时使用 64 KiB 构造缓冲，异常也恢复全局值，避免影响稍后 H264 PLAY。

这些是队列和单帧边界，不是整个进程 RSS 上限。还存在在途帧、参数缓存、
编码队列和 live555 的客户端/sink 内存；视频 sink/fragmenter 的内存比原先增加，
单客户端及多客户端真实内存仍需板测。本轮没有隐式增加客户端数量限制。

## 调试日志

约 10 秒运行快照增加：原始项数/字节、就绪完整帧/保留字节、累计丢帧、
等待 IDR、NAL 交付数及源错误。

```text
[lawrec-rtsp] runtime ... video_inputs_accepted=... video_units_ready=...
[rtsp-source] runtime ... raw_units=... ready_units=... retained_bytes=... wait_idr=... nal_deliveries=... error=...
[lawrec-rtsp] delivery failed ret=...
```

`video_inputs_accepted` 是原始队列接收；`video_units_ready` 是解析并入队的帧；
`nal_deliveries` 是完整 NAL 交给 live555 `afterGetting()`，不是 RTP 发包/客户端 ACK。
队列快照分别在对应锁下读取，不保证两队列处于同一瞬间。

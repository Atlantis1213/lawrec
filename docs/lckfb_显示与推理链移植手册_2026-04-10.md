## 二、必须先理解的系统关系

### 1. `lawrec` 不是板子真正直接运行的 ELF 名字

源码里我们开发的是：

- `src/reference/business_poc/lawrec/big/out/lawrec.elf`

但真正会被 RT-Smart 启动的是：

- `src/big/rt-smart/userapps/root/bin/fastboot_app.elf`

这意味着：

- `make lawrec` 编译成功，不代表板子已经会跑新代码
- 只有当 `lawrec.elf` 被复制覆盖为 `fastboot_app.elf`，并重新进 ROMFS，板子才会运行到最新逻辑

本轮已经修过这个链路，所以后续要优先检查：

1. `lawrec.elf` 是否更新
2. `fastboot_app.elf` 是否同步更新
3. `ROMFS` 是否重新打包

### 2. 板子启动读取的是 ROMFS，不是源码目录里的明文文件

例如：

- 你在源码里改了 `init.sh`
- 你在源码目录里看到了 `retinaface.kmodel`
- 这些都不等于板子真的会读取到这些文件

真正启动链是：

1. `src/big/rt-smart/userapps/root/bin/*`
2. `mkromfs.py`
3. `src/big/rt-smart/kernel/bsp/maix3/applications/romfs.c`
4. `rtthread.bin`
5. `big-core/rtt_system.bin`
6. 最终镜像

所以凡是涉及以下内容的改动：

- 大核 ELF
- 模型文件
- 启动脚本
- ROMFS 内资源

都必须重新走完整 ROMFS 构建链。

## 四、显示链如何正确移植

### 1. `lckfb` 显示参数必须统一

`lckfb` 下需要统一以下事实：

- 面板分辨率是 `480x800`
- 程序的显示层输入采用横屏逻辑 `800x480`
- 最终通过 `K_ROTATION_90` 旋转到实际面板方向

所以：

- 视频层 act size：
  - 宽：`800`
  - 高：`480`
- OSD 缓冲：
  - 宽：`480`
  - 高：`800`

### 2. 必须修改的显示侧项目

#### `main.cc`

需要加上 `lckfb` 分支：

- `connector_type = ST7701_V1_MIPI_2LAN_480X800_30FPS`
- `DISP_ROTATION = K_ROTATION_90`

#### `vi_vo.h`

需要为 `lckfb` 明确指定：

- `ISP_CHN0_WIDTH  = 800`
- `ISP_CHN0_HEIGHT = 480`
- `osd_width       = 480`
- `osd_height      = 800`

不要偷懒复用 `1080x1920` 旧值，否则极容易出现：

- 半屏
- 错位
- 乱码
- OSD 与预览不重合

### 3. `lckfb` 下 OSD 和 VO 线框不要同时开

本轮已经确认，在 `lckfb` 下如果同时使用：

1. `kd_mpi_vo_draw_frame()`
2. OSD 上的 OpenCV 画框

会出现明显的双框现象：

- 蓝框
- 白框

正确处理方式：

- `lckfb` 下只保留 OSD 白框
- 关闭 `VO draw_frame` 线框

如果未来需要调试映射：

- 可以临时打开 `VO draw_frame`
- 但不要和 OSD 常驻同时打开

### 4. 小框绘制必须使用浮点缩放

这是本轮非常关键的坑。

如果你在 `map_detect_box_to_osd()` 中写成这种整型风格：

- `((box.x2 - box.x1) * osd_height / ISP_CHN1_WIDTH)`
- `((box.y2 - box.y1) * osd_width / ISP_CHN1_HEIGHT)`

那么远处小脸框在缩放后很容易直接变成：

- `0` 像素宽
- `0` 像素高

这样就会出现：

- 日志里已经有检测框
- 屏幕上却完全看不到

正确做法：

- 全部先转成 `float`
- 最终绘制前再取整
- 并给缩放后宽高加一个最小值保护

建议策略：

- `w > 0 && w < 2` 时，设为 `2`
- `h > 0 && h < 2` 时，设为 `2`

## 五、摄像头和采集链如何正确移植

### 1. 传感器配置

`lckfb` 下已验证稳定的传感器选择是：

- `GC2093_MIPI_CSI2_1920X1080_30FPS_10BIT_LINEAR`

对应输入尺寸：

- `ISP_INPUT_WIDTH  = 1920`
- `ISP_INPUT_HEIGHT = 1080`

### 2. chn0 和 chn1 的用途

#### chn0

用途：

- 预览显示输出

配置：

- 尺寸：`800x480`
- 格式：`PIXEL_FORMAT_YVU_PLANAR_420`

#### chn1

用途：

- AI 输入

配置：

- 尺寸：`1280x720`
- 格式：`PIXEL_FORMAT_RGB_888_PLANAR`

### 3. 采集链最容易改错的三项

本轮已经验证，以下组合必须尽量和 sample 对齐：

1. `chn1.pix_format = PIXEL_FORMAT_RGB_888_PLANAR`
2. `kd_mpi_vicap_dump_frame(..., VICAP_DUMP_YUV, ...)`
3. `kd_mpi_vicap_set_database_parse_mode(..., VICAP_DATABASE_PARSE_XML_JSON)`

如果改偏，比如：

- `PIXEL_FORMAT_BGR_888_PLANAR`
- `VICAP_DUMP_RGB`
- `VICAP_DATABASE_PARSE_HEADER`

就容易出现：

- `dump_frame failed`
- 模型输入异常
- 检测链完全不稳定

经验：

- 采集链优先贴近 `sample/fastboot_app`
- 不要在未验证时发散尝试其他像素格式组合

## 六、推理链如何正确移植

### 1. `retinaface.kmodel` 本身没有问题

本轮已经验证：

- `src/big/kmodel/door_lock/retinaface.kmodel`
- `src/big/kmodel/mobile_retinaface/test.kmodel`
- `src/big/rt-smart/userapps/root/bin/retinaface.kmodel`

三者 md5 一致。

也就是说：

- 不要把问题优先归因到模型文件拿错
- 真正的问题主要出在：
  - 输入 pad
  - decode 路径
  - 阈值
  - 绘制

### 2. 一开始最危险的信号：`NaN` / 超大框 / 满屏乱框

如果日志出现：

- `raw_box0 non-finite`
- `box0=(2147483647,2147483367)-...`
- `detect boxes=几百/上千`

优先判断为：

- 原始 decode 结果已经坏了

不要先去改：

- OSD
- 画框坐标
- VO 映射

因为这类现象的根因几乎总在检测链上游。

### 3. `RVV` 路径当前不能用

本轮板端已经验证：

- `ENABLE_RVV 1` 时，`retinaface` 会出现异常值和坏框
- 切换到标量路径后，异常值问题才消失

所以当前稳定方案必须固定：

- `ENABLE_RVV 0`

文件位置：

- `src/reference/business_poc/lawrec/big/util.h`

经验：

- 后续除非单独重新验证 RVV 结果正确
- 否则不要为了性能恢复 `RVV`

### 4. `Model` 基类必须保留 `input_shape()`

这一点非常重要。

`MobileRetinaface` 的 ai2d 输出 shape 必须从：

- `input_shape(0)`

获取，而不是简单依赖：

- `ai2d_out_tensor_.shape()`

因此 `model.h / model.cc` 中必须保留：

- `dims_t input_shape(size_t idx);`

否则：

- pad 计算容易跑偏
- ai2d 输入输出关系会和 sample 失真

### 5. pad 必须用动态计算，不要靠板型硬编码

最终稳定写法不是：

- `lckfb` 走某个固定 pad 宏

而是：

1. 读取模型输入 shape
2. 根据 `height/width` 和模型输入尺寸算 `ratio`
3. 得到：
   - `h_pad_before/h_pad_after`
   - `w_pad_before/w_pad_after`
4. 把这组值喂给 ai2d pad

对当前 `1280x720 -> 320x320` 而言，本质上会得到：

- 宽缩放到 `320`
- 高缩放到 `180`
- 上下 pad 各 `70`

但不要把这个写死成常量，应该让代码自己算出来。

### 6. 检测阈值不是固定真理，要结合目标距离调

本轮实际走过的阈值如下：

- `0.60`
  - 近距离有框
  - 远距离小脸经常没框
  - 临界状态容易闪烁
- `0.50`
  - 好一些，但远脸仍然偏弱
- `0.35`
  - 远近都能更稳定出框

当前建议基线：

- `obj_threshold_ = 0.35`

文件：

- `src/reference/business_poc/lawrec/big/mobile_retinaface.h`

注意：

- 后续如果误检增多，不建议第一反应又把尺寸过滤加回来
- 更建议加“时序稳定”或“连续多帧确认”的逻辑

## 七、远处小脸不显示，实际可能有哪几层原因

本轮已经实战验证，远处小脸不显示至少可能由三层问题叠加导致：

### 1. 阈值过高

表现：

- `conf_max` 经常只有 `0.4~0.5`
- `above_thr(0.60)=0`

处理：

- 降低 `obj_threshold_`

### 2. 业务层最小框过滤

曾经在：

- `main.cc -> is_valid_detect_box()`

存在：

- `if (w < 24 || h < 24) return false;`

这会直接把远处小框扔掉。

最终必须删除。

### 3. OSD 缩放整型截断

即使上面两关都过了，如果绘制时仍用整型除法，小脸框仍会被压成 0 像素，看起来还是“没显示”。

所以：

- 检测能出小框
- 不等于屏幕上就一定能看见小框

这也是本轮反复出现“明明改了还像没变化”的真正原因之一。

## 八、退出和稳定性问题

### 1. 自启动场景里，`getchar()` 不可靠

本轮早期出现过：

- 输入 `q` 没反应
- `Ctrl+C` 后线程异常
- 甚至伴随 `stack overflow`

最终稳定策略：

1. 优先读取 `/dev/tty`
2. 回退再用 `getchar()`
3. `SIGINT` 时主动设置：
   - `app_run = false`

如果重新做移植，建议直接沿用这套退出逻辑，不要回退到只用 `getchar()`。

## 九、构建、打包和烧录的正确做法

### 1. 编译必须走 Docker

本轮统一使用的 Docker 命令模板如下。

单编 `lawrec`：

```bash
docker run --rm --user 1000:1000 \
  -v /home/atlantis/k230_sdk:/home/atlantis/k230_sdk \
  -v /home/atlantis/k230_sdk/toolchain:/opt/toolchain \
  -w /home/atlantis/k230_sdk \
  k230_docker:latest \
  bash -lc 'make CONF=k230_canmv_lckfb_defconfig lawrec'
```

整链打包：

```bash
docker run --rm --user 1000:1000 \
  -v /home/atlantis/k230_sdk:/home/atlantis/k230_sdk \
  -v /home/atlantis/k230_sdk/toolchain:/opt/toolchain \
  -w /home/atlantis/k230_sdk \
  k230_docker:latest \
  bash -lc 'make CONF=k230_canmv_lckfb_defconfig rt-smart-apps rtt_update_romfs big-core-opensbi build-image'
```

### 2. 每次改大核逻辑后必须走的顺序

只要改了这些内容中的任何一项：

- 大核 C/C++ 源码
- 大核模型
- 启动脚本
- OSD/ROMFS 资源

都必须至少执行：

1. `make ... lawrec`
2. `make ... rt-smart-apps`
3. `make ... rtt_update_romfs`
4. `make ... big-core-opensbi`
5. `make ... build-image`

不要省略 `rt-smart-apps`。

### 3. 优先只刷 RTT 分区

本轮联调已经反复验证：

- 大部分大核问题只需要刷：
  - `rtt_system.bin`

优点：

1. 联调快
2. 不影响小核 rootfs
3. 不容易引入整卡烧录变量

只有在这些情况才建议整卡重烧：

- 小核也改了
- 分区布局变了
- rootfs 资源变了

## 十、如何验证你烧进去的真的是最新版本

每次板测至少做这几步：

### 1. 看 build tag

启动日志里必须出现：

- `[lawrec] build_tag=...`

如果 build tag 不对，后续所有日志都没有分析价值。

### 2. 看 ELF 是否真的进了 ROMFS

宿主机上检查：

```bash
strings /home/atlantis/k230_sdk/src/reference/business_poc/lawrec/big/out/lawrec.elf | rg 'lawrec-lckfb'
strings /home/atlantis/k230_sdk/src/big/rt-smart/userapps/root/bin/fastboot_app.elf | rg 'lawrec-lckfb'
md5sum /home/atlantis/k230_sdk/src/reference/business_poc/lawrec/big/out/lawrec.elf \
       /home/atlantis/k230_sdk/src/big/rt-smart/userapps/root/bin/fastboot_app.elf
```

要求：

1. 两个 ELF 的 build tag 一致
2. 两个 ELF 的 md5 一致

### 3. 看板端关键日志

以后遇到问题，最有价值的是这几类日志：

- `build_tag`
- `retinaface ai2d in=... out=... pad_h=... pad_w=...`
- `retinaface conf_max=... above_0.3=... above_thr(...)=...`
- `detect boxes=...`
- `draw boxes=...`
- `box0=(...)-(...)`
- `raw_box0 x=... y=... w=... h=...`

这些信息足够判断问题落在哪一层：

1. pad/输入链
2. 阈值/检测链
3. 后处理
4. 绘制链

## 十一、推荐排障顺序

后续再遇到问题，不要乱改，按这个顺序排：

### 场景 A：屏幕不正常

先查：

1. `connector_type`
2. `DISP_ROTATION`
3. `ISP_CHN0_WIDTH/HEIGHT`
4. `osd_width/osd_height`
5. 是否同时开启了 VO 线框和 OSD

### 场景 B：检测 0 框

先查：

1. `build_tag` 是否正确
2. `retinaface ai2d` pad 是否合理
3. `conf_max` 大小
4. `obj_threshold_`
5. 采集链是否仍是 sample 稳定组合

### 场景 C：日志有框但屏幕没框

先查：

1. `detect boxes`
2. `draw boxes`
3. `map_detect_box_to_osd()` 是否还在用整型除法
4. 小框宽高是否被压成 0

### 场景 D：框乱飞 / NaN / 超大值

先查：

1. 是否误开了 `RVV`
2. pad 是否错误
3. decode 输出是否非有限值
4. 不要优先怀疑 OSD

## 十二、当前建议作为新环境起步时的最小动作

1. 从 `doorlock` 复制出 `lawrec`

4. 确保采集链回到 sample 稳定组合
5. 确保 `Model` 基类保留 `input_shape()`

   - `ENABLE_RVV 0`

## 十四、最后的建议

后续如果继续移植 `doorlock` 的完整业务，建议策略是：

1. 把当前 `2245-smallface-drawfix` 作为大核稳定底座
2. 暂时不要再大改显示链和 retinaface 主链

   - 人脸识别链

5. 每次板测都至少记录：
   - build tag
   - detect boxes
   - draw boxes

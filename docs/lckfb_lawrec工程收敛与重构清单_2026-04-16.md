# lckfb lawrec工程收敛与重构清单

## 1. 文档目标

本文档用于回答一个当前阶段的关键决策：

- 是否要放弃现有 `lawrec` 工程，重新起一个全新框架？

当前结论明确如下：

- 不建议现在重开新框架。
- 建议继续基于当前已经跑通的 `lawrec` 工程迭代。
- 但必须尽快做一次“去 `doorlock` 化 + 模块化收敛”。

后续开发统一按本文档清单推进。

## 2. 当前判断

### 2.1 为什么不建议现在重开框架

当前 `lawrec` 已经跑通了以下基础能力：

- 小核 UI 显示
- 大小核 IPC 通信
- 大核显示链
- 大核人脸识别程序
- 小核对大核的页面联动控制

这些能力的价值非常高，因为它们已经覆盖了一个 K230 双核项目最难跑通的底座部分。

如果现在重开框架，会面临以下高风险：

- 重新踩一遍启动链、显示链、IPC 链、打包链
- 重新暴露大量之前已经解决的兼容性问题
- 当前功能开发节奏被打断
- 很多“曾经修好但没完全文档化”的细节容易丢失

因此当前阶段最优策略不是“推倒重来”，而是“在跑通基础上清理和收敛”。

### 2.2 为什么不能继续无约束地沿用 `doorlock`

当前 `lawrec` 的大核工程仍然保留了较多 `doorlock` 结构和语义残留，如果继续不加约束地开发，后面会出现以下问题：

- 业务语义混乱
- 主程序越来越臃肿
- 功能耦合越来越强
- RTSP、录像、取证、页面联动等新功能难以接入
- 后续排障时很难分清“当前业务代码”和“历史母项目遗留代码”

因此必须做一次结构化清理。

## 3. 总体策略

后续统一采用以下策略：

1. 冻结当前可运行版本，作为回退基线。
2. 在现有 `lawrec` 工程上做去 `doorlock` 化清理。
3. 先完成单进程模块边界收敛，再继续叠加 RTSP 等新功能。
4. 除非后续确认现有工程已经无法维护，否则不重新起框架。

## 4. 执行优先级

本清单分为三层：

- P0：必须先做，不做后面会越来越乱
- P1：建议尽快做，利于后续 RTSP/录像/业务功能扩展
- P2：可以延后做，不阻塞当前主线

## 5. P0 必做清单

### P0-1 冻结当前可运行基线

目标：

- 保留当前已跑通版本，避免后续重构时丢失可用状态。

动作：

- 备份当前 `lawrec` 工程目录
- 记录当前可启动镜像产物路径
- 记录当前大核 elf 路径
- 记录当前小核 UI 可运行版本
- 在 `开发记录.md` 中补一条“可回退版本说明”

验收标准：

- 任意后续修改失败时，能够快速回退到当前可运行状态。

### P0-2 清理工程命名残留

目标：

- 让工程语义从 `doorlock` 切换为 `lawrec`，避免后续开发持续混淆。

重点清理内容：

- 工程名
- bin 名称
- 日志前缀
- IPC 服务名
- 宏名
- 注释中的 `doorlock/door_lock`

特别说明：

- 如果某些 IPC 名称短期内与对端有兼容关系，可以先保留通信兼容，但要在代码中明确标注“历史兼容保留项”。

验收标准：

- 新增功能不再出现 `doorlock` 语义扩散。

### P0-3 识别并标记“历史母项目代码”和“当前业务代码”

目标：

- 先把代码分层看清，再决定删什么、保什么。

动作：

- 在大核工程中标记当前确实在使用的模块
- 标记“仍在编译但当前业务未使用”的模块
- 标记“只为兼容保留”的路径

建议分类：

- 当前核心模块
- 当前兼容保留模块
- 待删除模块

验收标准：

- 每个主要源文件都能明确回答“为什么还保留它”。

### P0-4 收敛大核 `main.cc`

目标：

- 停止把新功能继续直接堆到 `main.cc`。

当前问题：

- `main.cc` 已经承担了过多职责，包括显示、预览、IPC、AI、状态切换等。

动作：

- 禁止在 `main.cc` 中继续直接写大块新业务逻辑
- 后续新增功能必须先落模块，再由 `main.cc` 调用
- 先把“预览控制”“IPC 处理”“AI 开关”“启动流程”整理成独立函数或模块

验收标准：

- `main.cc` 主要只做初始化、状态机、模块调度。

### P0-5 明确当前大核的功能边界

目标：

- 给接下来的 RTSP、录像、拍摄页面开发一个稳定边界。

当前建议边界：

- 大核负责：
  - 摄像头采集
  - 显示链与预览控制
  - 编码
  - AI 推理
  - IPC 被控执行
- 小核负责：
  - 单进程主应用
  - UI
  - 输入事件
  - 页面切换
  - RTSP server
  - 向大核发送控制命令
  - 显示状态与业务状态机

验收标准：

- 新功能设计时，不再反复摇摆“这部分应该放大核还是小核”。

### P0-6 关闭当前无关业务主线

目标：

- 暂时关掉与当前主线无关但容易造成干扰的流程。

建议先收敛的部分：

- 无关的人脸库管理流程
- 与门锁业务相关的注册/删除/导入逻辑
- 当前不需要的开机自动动作
- 与当前取证主线无关的 UI 入口

验收标准：

- 当前主线只保留“显示、拍摄、IPC、预览、后续 RTSP 预留”。

## 6. P1 建议尽快做的清单

### P1-1 建立大核模块目录

目标：

- 不再让大核工程平铺在一个目录里无限增长。

建议模块：

- `big/src/display`
- `big/src/ipc`
- `big/src/ai`
- `big/src/preview`
- `big/src/common`

说明：

- `big/src/rtsp` 在 2026-04-16 之后不再作为正式主线保留方向。
- 大核 RTSP 只保留兼容状态/历史痕迹，不再继续扩展为正式 server 模块。

说明：

- 这一步不要求一次重构到底，但新功能必须按这个方向落地。

验收标准：

- 新增 RTSP 模块时，不需要再塞回根目录。

### P1-2 建立统一状态机

目标：

- 统一管理预览、RTSP、AI、页面联动关系。

建议先定义的状态：

- `preview_enabled`
- `rtsp_enabled`
- `ai_enabled`
- `record_enabled`

后续可演进为：

- `IDLE`
- `PREVIEW_ONLY`
- `PREVIEW_AND_RTSP`
- `PREVIEW_AND_RECORD`
- `PREVIEW_AI_RTSP`

补充说明：

- 这套状态机的 owner 应放在小核单进程主应用控制模块，而不是分散在 `ui` 进程、`service` 进程、本地 socket 三处。

验收标准：

- 进入拍摄、退出拍摄、启动 RTSP、关闭 RTSP 不再靠散落布尔变量硬拼。

### P1-3 收敛 IPC 协议

目标：

- 把 IPC 从“能跑”演进成“可维护”。

动作：

- 整理现有 IPC 命令表
- 给每条命令明确：
  - 命令号
  - 发起方
  - 接收方
  - 参数结构
  - 返回结构
  - 超时策略

后续新增命令建议：

- 预览进入/退出
- RTSP 开始/停止
- RTSP 状态查询
- 录像开始/停止

验收标准：

- IPC 协议不再依赖“看日志猜行为”。

### P1-4 把 AI 流程从显示/预览流程中解耦

目标：

- 防止后续出现“开预览必须跑 AI”“关 AI 影响显示”的问题。

建议：

- 预览链和 AI 链逻辑上拆开
- AI 是否开启由显式状态控制
- 首版 RTSP 默认不依赖 AI

验收标准：

- 预览、AI、RTSP 三者可以分开控制。

### P1-5 建立 `lawrec` 自己的媒体模块

目标：

- 不再长期直接复用 sample 风格流程。

建议拆出的模块：

- `preview_controller`
- `venc_pipe`
- `rtsp_session`

验收标准：

- RTSP 开发时直接围绕 `lawrec` 模块做，而不是继续在 sample 代码里打补丁。

### P1-6 清理启动链和自启动逻辑

目标：

- 启动流程可控，不再出现“谁在自动启动、谁在抢占资源”不明确的问题。

动作：

- 统一记录小核启动脚本
- 统一记录大核自启动逻辑
- 明确哪些功能开机自启，哪些功能手动进入页面后启用

当前建议：

- 大核底层显示链可自启
- 摄像头预览不要默认直出
- RTSP 不要默认自启
- AI 不要默认满负载运行

验收标准：

- 开机行为可解释、可关闭、可复现。

## 7. P2 可延后清单

### P2-1 进一步拆分公共工具层

目标：

- 把工具类、公共宏、公共日志从业务文件中抽离。

包括：

- `util`
- 日志宏
- 错误码定义
- 时间统计工具

### P2-2 统一配置管理

目标：

- 把当前硬编码参数逐步收敛。

包括：

- 分辨率
- 旋转角度
- UI 页面进入时的动作
- RTSP 默认端口和 stream 名
- AI 开关默认值

### P2-3 建立更完整的目录规范

建议后续目标结构：

- `big/src`
- `big/include`
- `little/ui`
- `little/ipc`
- `docs`
- `scripts`

### P2-4 补充专项文档

建议后续形成单独文档：

- IPC 协议文档
- 启动链文档
- RTSP 模块设计文档
- 录像模块设计文档
- 大核显示链文档

## 8. 后续开发建议顺序

建议按以下顺序执行，不建议跳步。

### Step 1

先冻结当前基线版本。

### Step 2

完成 P0-2 到 P0-6 的清理，让工程语义和功能边界先稳定。

### Step 3

建立大核模块目录和统一状态机。

### Step 4

按“官方 RTSP 双核架构”推进 RTSP：

- 大核负责采集和编码
- 小核负责 RTSP 网络服务控制或协作侧逻辑
- 参考官方 RTSP 教程与 sample 实现

### Step 5

RTSP 跑通后，再继续录像、取证业务、页面联动等正式功能。

## 9. 接下来必须遵守的开发规则

从本文档开始，后续开发统一遵守以下规则：

1. 不再直接往现有 `main.cc` 无限制堆逻辑。
2. 新功能优先模块化落地。
3. 任何保留的 `doorlock` 代码都要能说明保留原因。
4. 任何新的大小核职责划分都要先明确边界。
5. 先跑通主链路，再做增强功能。
6. 不为短期省事继续扩大历史包袱。

## 10. 最终结论

最终结论明确如下：

- 当前不重开框架。
- 当前继续基于 `lawrec` 演进。
- 但立刻开始做“去 `doorlock` 化 + 模块化收敛”。
- 接下来所有功能开发，都要建立在这次收敛清单之上。

本文档可以作为后续开发的总 checklist 使用。

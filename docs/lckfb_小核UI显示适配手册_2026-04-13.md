## 一、先说最终结论

本轮最终确认的事实如下：

1. `lckfb` 下 little Linux 不是“纯代理”
   - `canaan-drm` 会直接写 VO 的 OSD4~7
   - 不是简单的“Linux 只做一个假 DRM 入口”

2. 当前异构显示职责划分是：
   - big：
     - 负责 connector / panel / mode / preview
   - little：
     - 负责往 DRM plane 提交 LVGL UI framebuffer

3. 官方 little LVGL 可用项目：
   - `door_lock`
   - `peephole_device`
   - `peephole_phone`
   都固定使用：
   - `DRM_UI_BUF_USE_PLANE = 2`
   - 在当前驱动里对应 `plane id 33`

4. `lawrec` 一开始之所以一直不显示，不是 UI 没启动，而是自己把 little 显示逻辑改偏了：
   - 增加了 LCKFB 下自动 plane 选择
   - 自动选到了 `plane_idx=4 plane_id=35`
   - 这偏离了官方已验证工作路径

5. 最终有效方案不是继续加策略，而是：
   - 把 `lawrec` 的 little 显示逻辑严格收回到 `door_lock` 原始路径
   - 固定 `plane_idx = 2`
   - 恢复 `screen_transp = 1`
   - 恢复第一次有效 flush 后再 `plane_config()`
   - 恢复单段 `plane_config()` / `plane_update()` 模型

6. 当 little UI 终于显示出来后，新的问题已经不再是 DRM，而是 UI 自己的布局设计：
   - 主界面原本就是底部半透明小 panel
   - 在 `480x800` 上看起来会“都挤在下方”
   - 需要继续把 `scr_main.c` 的布局改成更适合当前屏幕尺寸的版本

## 二、必须先理解的关键系统关系

### 1. 整个 little UI 显示链路到底怎么走

本轮最终确认，`lawrec` 在 `lckfb` 上的小核 UI 显示链路是下面这样：

1. little Linux 启动
2. `S99lawrec` 拉起：
   - `/app/lawrec/ui/ui`
3. `ui` 程序初始化 LVGL
4. LVGL 调用 little 侧显示适配：
   - `lv_port_disp.cpp`
5. `lv_port_disp.cpp` 通过 DRM/KMS：
   - 打开 `/dev/dri/card0`
   - 创建 framebuffer
   - 把 UI 缓冲提交到固定 plane
6. `canaan-drm` 驱动把该 plane 对应写入：
   - VO OSD4~7
7. big 侧已经提前完成：
   - connector
   - panel
   - mode
   - preview
8. 最终屏幕显示为：
   - big 预览作为底图
   - little LVGL UI 作为叠加层

这个链路里最容易误判的地方有两个：

1. little 不是单独点屏
   - panel / mode owner 仍是 big
2. little 也不是“纯软件代理”
   - `canaan-drm` 会直接写 VO OSD4~7

所以对这块系统的正确理解应该是：

- big 负责显示底座
- little 负责把 UI 贴到固定的 overlay plane 上

### 2. 真正应该看哪几层

以后遇到 little UI 显示问题，优先把问题归到这三层之一：

1. 进程层
   - `ui` 是否启动
   - `S99lawrec` 是否拉起

2. 提交层
   - `lv_port_disp.cpp` 是否把 framebuffer 提交到正确 plane
   - `liblv_drivers.so` 是否是最新版本

3. 布局层
   - `scr_main.c`
   - `scr_signup.c`
   - `scr_ota.c`

如果板上“完全没有 UI”，先查前两层。

如果“UI 有了但位置不对”，直接查第三层，不要再绕回 DRM。

### 1. 小核 UI 真正显示靠的不是 `ui` 主程序本体

这是本轮最重要的坑之一。

看起来板上启动的是：

- `/app/lawrec/ui/ui`

但真正负责 DRM / LVGL 显示提交逻辑的，不是这个 ELF 本身，而是它链接到的共享库：

- `/usr/lib/liblv_drivers.so`

这意味着：

- 你看到 `ui` 二进制时间戳更新
- 不等于显示逻辑就真的更新了

必须同时检查：

1. `ui`
2. `liblv_drivers.so`

如果 `ui` 更新了，但 `liblv_drivers.so` 还是旧的，那么板上仍然会继续跑旧显示逻辑。

### 2. little UI 的真正核心文件在哪里

本轮最终确认，little UI 显示链最关键的是这两个文件：

- `src/little/buildroot-ext/package/lawrec/src/ui/lvgl_port/k230/lv_port_disp.cpp`
- `src/little/buildroot-ext/package/lawrec/src/ui/src/scr_main.c`

职责分工：

- `lv_port_disp.cpp`
  - DRM plane 选择
  - framebuffer 创建
  - atomic commit 时序
  - flush 和 vsync 提交链

- `scr_main.c`
  - 主界面布局
  - 主 panel 样式
  - 图标按钮位置
  - 标题和状态文本位置

如果“不显示”，优先看 `lv_port_disp.cpp`。

如果“能显示，但都挤在底部”，优先看 `scr_main.c`。

### 3. big / little 与庐山派屏驱动的实际关系

这部分本轮也反复走过弯路，必须单独说明。

当前 `lckfb` 的真实硬件是：

- ST7701
- `480x800`

big 侧已经完成了：

- `connector_type = ST7701_V1_MIPI_2LAN_480X800_30FPS`
- `K_ROTATION_90`
- 预览链和显示底座初始化

而 little 侧本轮最终确认：

- 不要去争夺 panel owner
- 不要再让 little Linux 去完整接管 ST7701 panel
- 不要再把 little Linux 当成“真正决定 mode 的一方”

换句话说：

- 庐山派的 ST7701 真正由 big 侧点亮
- little 只是利用 `canaan-drm` 提交 overlay

这就是为什么本轮最终放弃了“继续推进 little Linux ST7701 完整 owner 路线”。

## 三、庐山派驱动适配到底做了什么

### 1. big 侧真正保留了什么

对庐山派的真正有效驱动适配，保留在 big 侧：

1. 面板类型切到：
   - `ST7701_V1_MIPI_2LAN_480X800_30FPS`
2. 显示旋转切到：
   - `K_ROTATION_90`
3. 预览显示尺寸统一到：
   - `800x480`
4. OSD 尺寸统一到：
   - `480x800`

这些已经在：

- `big/main.cc`
- `big/vi_vo.h`

对应的大核手册里单独沉淀过。

### 2. little 侧试过哪些路线

本轮 little 侧一共试过两类路线：

#### 路线 A：让 little Linux 去认 ST7701 / 接管 panel

尝试内容包括：

- 检查 `k230_canmv_lckfb.dts`
- 检查 `panel-sitronix-st7701.c`
- 尝试让 little DTS 绑定到 ST7701
- 尝试把 little DRM mode 改成真实的 `800x480`

这条路线最后没有作为本轮结论保留，原因有三点：

1. 当前异构职责边界不适合这样做
   - big 已经在正常点屏
   - little 再接管 panel owner 容易把职责搞乱

2. 当时的核心目标不是“重建 little 完整 panel 栈”
   - 而是“让 existing little UI 出现在当前大核显示底座上”

3. 继续推进这条路线，会把问题从“UI 显示链”扩散成“整套 panel/connector ownership 重构”
   - 成本高
   - 风险大
   - 不适合当前阶段

#### 路线 B：按 `door_lock` 式异构职责收敛

最终保留的是这条路线：

- big 继续做 panel/mode owner
- little 只做 overlay plane client
- little 不再自作主张自动选 plane
- little 不再尝试扩展自己的显示所有权

这条路线最终被验证有效。

### 3. little 侧关于 `1080x1920` / `hx8399` 应该怎么理解

本轮必须特别说明这一点，因为它非常容易把人带偏。

板上你看到过这些现象：

- `/sys/class/drm/card0-DSI-1/modes`
  - `1080x1920`
- 或者 little DRM 里仍然能看到：
  - `hx8399`

这些现象的含义不是：

- 屏幕真的已经被 little 侧错误点成了 1080p

它更像是：

- little Linux 这边保留了一套占位式 panel / mode 认知
- 但当前真正的物理 panel owner 仍是 big

所以本轮最后的结论不是“把 little panel 驱动修到完全真实”，而是：

- 在当前 `lawrec` 异构职责下，先不要继续碰 little panel owner 路线
- 先把 little UI 提交链和布局跑通

### 4. 当前阶段对庐山派驱动适配的正确表述

如果要用一句话概括本轮对庐山派驱动到底做了什么，正确说法是：

- big 侧完成了 ST7701 / `480x800` / 旋转 / 预览底座适配
- little 侧没有继续争夺 ST7701 owner，而是回到官方 fixed plane 提交模型

这比笼统地说“把 little 的 ST7701 驱动补齐了”更准确。

## 四、前期 `CMA` 报错到底是怎么回事

### 1. 当时看到的关键日志是什么

早期板端启动日志里明确出现过：

- `cma: Failed to reserve 64 MiB`

同时还看到：

- Linux 实际可用内存非常紧
- 只有约 `128MB` 级别空间
- 当时还额外挂了：
  - `crashkernel`

这说明：

- 内核一开始就没能成功为 CMA 预留出所需的连续内存

### 2. 这个问题为什么当时是“必须先修”的

K230 的 VO / 多媒体链路对连续物理内存有明确依赖。

当时如果 CMA reserve 失败，会直接引发：

1. big 侧某些视频输出 / 显存分配不稳定
2. little 侧基于 DRM 的 framebuffer 分配也会更脆弱
3. 整个系统在低内存下更容易出现：
   - OOM
   - 提交异常
   - 行为不稳定

所以那个阶段把注意力放在：

- `CMA`
- `mem=`
- `reserved-memory`
- 内存切分

是完全正确的。

### 3. 当时怎么修的

本轮最终采用的方向是：

1. 去掉不必要的：
   - `crashkernel`
2. 把 CMA 从过大的 `64MB` 收缩到更适合当前 `lckfb` 内存布局的：
   - `32MB`

修完后，板端出现的正确信号是：

- `cma: Reserved 32 MiB at ...`
- `Memory: ... 32768K cma-reserved`

这说明：

- CMA 预留已经成功

### 4. 修完 CMA 之后，为什么 little UI 还是没显示

这正是本轮一个很关键的阶段性判断。

修完 CMA 后，说明：

- 底层连续内存问题已经不再是第一阻塞项

但 little UI 仍然不显示，说明问题已经进入下一阶段：

- 不是“内存 reserve 失败导致根本没法申请 buffer”
- 而是“little 自己的显示提交策略和官方工作路径不一致”

也就是说，`CMA` 问题和 `plane 误选` 问题，是两个不同层级的问题：

1. `CMA`
   - 是更底层的资源可用性问题
2. `plane / atomic 提交 / 布局`
   - 是 little UI 显示链自身问题

### 5. 当前应该怎么理解 `CMA` 与 little UI 的关系

本轮最终可以这么理解：

- `CMA` 曾经是必须先解决的前置稳定性问题
- 但在 `CMA reserve` 成功后，little UI 仍然不显示，已经证明：
  - 后续主因不再是 `CMA`

所以后面继续围绕 little 收敛时，正确做法是：

- 不再把“UI 不显示”的根因默认归到 `CMA`
- 而是直接查 little 提交链、产物更新链和布局层

这也是为什么本轮后来把主要精力从：

- `CMA / mem / reserved-memory`

切换到了：

- `lv_port_disp.cpp`
- `liblv_drivers.so`
- `scr_main.c`

## 五、本轮一开始为什么会跑偏

### 0. 分辨率问题这条线，完整是怎么演化的

这一轮里最容易把人带偏、也最值得单独记录的，就是“分辨率认知”这条线。

必须把下面几个数字分开理解：

- 物理屏真实参数：
  - `ST7701`
  - `480x800`
- big 显示输入逻辑：
  - `800x480`
  - 再通过 `K_ROTATION_90` 旋转到面板方向
- little DRM 一度读出来的 mode：
  - `1080x1920`
- little UI 真实想用的逻辑尺寸：
  - `480x800`

这几个数字混在一起时，就很容易得出错误结论。

#### 第 1 阶段：发现 little DRM 读出来是 `1080x1920`

当时板端能直接看到：

- `/sys/class/drm/card0-DSI-1/modes`
  - `1080x1920`
- `modetest -M canaan-drm -p -c`
  - connector mode 也是 `1080x1920`

与此同时，`lawrec` little UI 侧又已经在尝试按：

- `480x800`

去做自己的 UI 逻辑尺寸。

于是就出现了最典型的冲突：

- little DRM 认知的 mode 是 `1080x1920`
- little UI 希望的逻辑尺寸是 `480x800`

最开始很自然会怀疑：

- 既然模式错了，那就应该先把 little DRM / little DTS / little panel 驱动全修对

这就是后面一度走向 ST7701 owner 路线的起点。

#### 第 2 阶段：一度尝试让 little Linux 走 ST7701 owner 路线

当时做过的尝试包括：

1. 检查：
   - `k230_canmv_lckfb.dts`
2. 检查：
   - `panel-sitronix-st7701.c`
3. 尝试让 little DTS 从：
   - `hx8399`
   切到：
   - `ST7701`
4. 尝试让 little DRM 读出来的 mode 也变成真实的：
   - `800x480`
   或 `480x800`

这条路线在逻辑上并不荒谬，因为它试图解决的是：

- little 这边“对屏的认知”和真实硬件不一致

但后面联调越来越清楚后，发现这条路虽然“理论上更完整”，却不是当前异构系统下最合适的主方向。

#### 第 3 阶段：为什么后来放弃了 little ST7701 owner 路线

后来放弃这条路线，不是因为它在所有场景下都错，而是因为在当前 `lawrec + lckfb + big/little` 这套系统里，它不是最佳收敛方向。

原因有四个：

1. 当前真实 panel / mode owner 已经是 big
   - big 已经成功点亮 ST7701
   - big 预览已经正常

2. 当前目标不是重建一套全新的 little panel 栈
   - 而是让 little UI 叠加到现有 big 显示底座上

3. 如果继续推进 little owner 路线，问题会迅速扩散成：
   - DTS
   - panel driver
   - connector ownership
   - modeset 职责边界
   - big/little 冲突

4. 真实联调结果表明，little UI 最终能显示出来，并不依赖 little Linux 真正把 mode 修到 `480x800`
   - 它真正依赖的是：
     - 正确的 fixed plane 路径
     - 正确的 atomic 提交模型
     - 正确的 UI 逻辑尺寸

所以这条路线最后被明确收敛掉了。

#### 第 4 阶段：后来真正收敛成什么

最后真正有效的结论是：

1. big 做真实 panel / mode owner
   - 真实 ST7701
   - 真实物理屏
   - 真实 connector/mode 初始化

2. little 不再依赖：
   - `/sys/class/drm/card0-DSI-1/modes`
   - 也不再把 `1080x1920` 当成 UI 逻辑尺寸来源

3. little 只保留自己真正需要的三件事：
   - 固定 UI 逻辑尺寸：
     - `480x800`
   - 固定提交到官方已验证的 plane：
     - `DRM_UI_BUF_USE_PLANE = 2`
   - 固定走 `door_lock` 式 atomic 提交模型

也就是说，最后的正确收敛不是：

- “先把 little DRM 的模式完全修真实”

而是：

- “先承认 big 才是 mode owner，little 只做 fixed plane client”

#### 第 5 阶段：现在应该如何理解这几个尺寸

到本轮最后，可以把几个尺寸关系理解成下面这样：

1. `480x800`
   - 物理屏真实方向
   - little UI 的最终逻辑尺寸

2. `800x480`
   - big 侧显示输入的横屏逻辑
   - big 再通过旋转输出到物理屏

3. `1080x1920`
   - little DRM 这侧一度枚举出来的占位式 mode
   - 不能继续拿来作为 little UI 逻辑尺寸依据

#### 第 6 阶段：这条分辨率线最后带来的工作原则

以后在这块系统上再遇到分辨率相关问题，优先按下面原则判断：

1. 如果问题是 big 预览 / panel / connector 本身不正常
   - 去查 big
   - 去查真实 ST7701 / `800x480` / 旋转链

2. 如果问题是 little UI 不显示
   - 先不要再被 `1080x1920` 的 DRM mode 带偏
   - 先查 fixed plane 提交链

3. 如果问题是 little UI 能显示但布局奇怪
   - 那已经不是显示 mode 问题
   - 直接去查 `scr_main.c` 这类布局文件

### 1. 误以为 big OSD 抢了 little UI 的资源

一开始有一个直觉判断：

- big 正在用 OSD
- little UI 也在用 overlay
- 所以可能是 big OSD 抢了 little 资源

后来通过实际验证确认：

1. big 当前使用的是：
   - OSD0~3
2. little 当前驱动能写的是：
   - OSD4~7
3. 因此 big OSD3 和 little UI 并不是同一路硬件资源

所以：

- “关掉 big OSD3 后 little UI 还不显示”
  不能证明 little 路没通
- 但可以证明：
  - big OSD3 不是主因

### 2. 误以为“只要选到了 overlay plane 就一定能显示”

本轮曾经在日志里看到：

- `selected plane_idx=4 plane_id=35`

于是很容易产生错觉：

- plane 都选上了，为什么还不显示？

后来确认：

- 选到了一个“可提交”的 plane
- 不等于它就是官方实际工作路径

官方几个可工作的 little UI 项目都统一固定：

- `DRM_UI_BUF_USE_PLANE = 2`

而 `lawrec` 当时自己加了“优先 overlay / 自动选择 zpos 更高 plane”的策略，结果反而从官方路径偏到了 `plane_idx=4`。

这类“聪明的自动策略”在这种异构板卡上非常危险。

本轮最终结论是：

- 先不要做自动 plane 选择
- 先收回官方固定路径

## 六、本轮实际踩中的核心坑

### 1. 旧日志一直出现，不代表板子没烧新镜像

这个坑非常迷惑。

明明已经：

- 改了 `lv_port_disp.cpp`
- 重新打了镜像
- 重新烧了卡

但板端仍然一直打印旧日志：

- `prefer lckfb overlay plane_idx=4 plane_id=35`
- `selected plane_idx=4 plane_id=35`

一开始很容易怀疑：

- 是不是板子没真正烧进去

但后面查清楚后发现：

- 板子烧的是新镜像
- 问题在宿主机打包链

根因是：

- `lawrec` 包在 Buildroot 里使用了：
  - `rsync -au`
- 而 `-u` 会保留“被认为更新”的旧文件
- 于是 `output/.../build/lawrec/` 目录里的旧 `lv_port_disp.cpp` 没被新源码覆盖

结果就是：

1. 你改的是源码目录里的文件
2. 但真正参与编译的是 `output/.../build/lawrec/...` 里的旧副本
3. 编出来的 `liblv_drivers.so` 自然还是旧逻辑

### 2. 必须检查 `build/lawrec` 目录里的源码副本

本轮最终确认，排查这个问题时必须直接比这两份文件：

- 源码真实文件：
  - `src/little/buildroot-ext/package/lawrec/src/ui/lvgl_port/k230/lv_port_disp.cpp`
- Buildroot 包展开后的编译源：
  - `output/k230_canmv_lckfb_defconfig/little/buildroot-ext/build/lawrec/ui/lvgl_port/k230/lv_port_disp.cpp`

如果两者：

- 时间戳不一致
- 文件大小不一致
- 内容不一致

那就说明：

- 当前镜像不是用你刚改的源码编出来的

这一步是本轮真正把问题定位出来的关键。

### 3. `liblv_drivers.so` 才是最终判断标准

最终判断 little 显示逻辑是否真的更新，最直接的方法不是看源码，而是直接搜共享库字符串：

```bash
rg -a -n 'prefer lckfb overlay|selected plane_idx=|set zpos=7|set alpha=0xffff' \
  output/k230_canmv_lckfb_defconfig/images/little-core/rootfs/usr/lib/liblv_drivers.so
```

如果这些旧字符串还在，就说明：

- 旧 little 显示逻辑仍然在镜像里

如果这些旧字符串消失，才说明：

- 新 `lv_port_disp.cpp` 已经真正进入镜像

这个检查比看板子日志更可靠，因为它能在烧板前就把问题拦住。

## 七、本轮最终验证有效的显示收敛方案

### 1. 收敛原则

不要继续在 `lawrec` little 侧自创策略。

要做的是：

- 尽量贴近 `door_lock` 原始路径
- 先让 `lawrec` 变成“能正常显示的 little UI”
- 再做业务样式调整

### 2. `lv_port_disp.cpp` 最终有效的收敛点

最终对 `lawrec` 采取的是：

1. 固定：
   - `DRM_UI_BUF_USE_PLANE = 2`

2. 取消：
   - LCKFB 下自动 plane 选择
   - `prefer lckfb overlay`
   - 动态切换到 `plane 34/35`

3. 恢复：
   - `screen_transp = 1`

4. 恢复：
   - `door_lock` 的单段 `plane_config()`
   - `door_lock` 的单段 `plane_update()`

5. 恢复：
   - 首次完整 flush 后，再做一次 `plane_config()`

6. 去掉：
   - base/rect 两段 atomic commit
   - alpha/zpos 强制写入
   - 额外 plane probe 策略

### 3. 为什么不能保留自动 plane 选择

因为本轮已经实战证明：

- 自动选 overlay plane
- 听起来合理
- 但会把 `lawrec` 从官方已验证路径带偏

而当前这块板子的正确目标不是“找到看起来更高级的 plane”，而是：

- 先严格复刻官方可工作路径

这类异构显示场景里，稳定性比策略聪明更重要。

## 九、为什么 UI 显示出来后仍然“都挤在下方”

这不是 DRM 问题，而是主界面布局本身的问题。

### 1. `scr_main.c` 原始设计就是底部 panel

`lawrec` 当前主界面原本做成了：

- 底部半透明 panel
- 标题和状态放在 panel 顶部
- 四个按钮排在 panel 底边附近

在大屏或者半屏假设下，这种布局没问题。

但在 `480x800` 上，会表现成：

- 整个 UI 都集中在底部
- 看起来像“挤成一团”

### 2. 这不是“显示错位”，而是“布局风格不适合当前屏幕”

表现上很像：

- Y 坐标错了
- plane 偏移了

但本质上不是。

真正原因是：

- `scr_main.c` 里按钮位置和 panel 尺寸就是这么设计的

本轮调整的方向是：

1. 主 panel 从底部窄条，改为更高的中下区域卡片
2. 四个按钮从底部一排，改成 `2x2` 布局
3. 标题和状态文字边距适当放大

### 3. 本轮调整的关键文件

- `src/little/buildroot-ext/package/lawrec/src/ui/src/scr_main.c`

调整点包括：

- `scr_main_btn_signup/import/delete/ota` 的位置
- `scr_main_panel` 的尺寸和对齐
- 标题和状态文本的位置
- 按钮启停逻辑把 `OTA` 也统一纳入

## 十一、本轮最重要的构建与打包经验

### 1. 只改源码不够，必须验证包构建目录

每次改 little UI 后，至少要验证：

1. 源码目录里的文件变了
2. `build/lawrec/...` 里的文件也真的变了
3. `liblv_drivers.so` 里的旧字符串消失了
4. 最终镜像时间戳更新了

否则就很容易出现：

- 你以为已经修了
- 其实镜像里还是旧逻辑

### 2. 如果怀疑 Buildroot 没同步源码，最稳妥的办法是删包重打

本轮最终有效的做法是：

```bash
docker run --rm -u root \
  -v /home/atlantis/k230_sdk:/home/atlantis/k230_sdk \
  -v /home/atlantis/k230_sdk/toolchain:/opt/toolchain \
  -w /home/atlantis/k230_sdk \
  ghcr.io/kendryte/k230_sdk \
  /bin/bash -lc 'rm -rf output/k230_canmv_lckfb_defconfig/little/buildroot-ext/build/lawrec && make CONF=k230_canmv_lckfb_defconfig buildroot build-image'
```

这一步的意义是：

- 先把旧 `build/lawrec` 整目录清掉
- 避免 `rsync -au` 留下旧编译源
- 强制让 Buildroot 重新 extract / configure / build / install `lawrec`

### 3. 不能只盯 `ui` 二进制

这一点再次强调。

真正决定显示行为的是：

- `liblv_drivers.so`

所以每次 little 显示链修改后，都应该检查：

```bash
rg -a -n 'prefer lckfb overlay|selected plane_idx=|set zpos=7|set alpha=0xffff' \
  output/k230_canmv_lckfb_defconfig/images/little-core/rootfs/usr/lib/liblv_drivers.so
```

如果搜出来了，说明你仍在跑旧逻辑。

重点关注：

- panel 尺寸
- `LV_ALIGN_BOTTOM_MID`
- 按钮 `pos.x / pos.y`
- 文本位置

### 场景 D：改了 UI 位置，但上板没变化

优先怀疑：

- `scr_main.c` 没真的重新进入 `build/lawrec`
- 新布局没真的编进镜像

不要先怀疑板子。

# K230 庐山派触控异常：从发现、定位到修复的完整复盘

记录日期：2026-10-02。基于本项目源码、阶段文档和实际调试反馈整理。

本文既是工程复盘，也是回答“你开发过程中遇到的最困难的问题是什么？如何解决？”的素材。
面试可以突出主动定位、实验设计和跨层分析，但不要把尚未验证的结论包装成事实。

## 1. 一句话概括

**在 K230 大小核协同项目中，触控单独测试正常，显示输出开启后却出现迟钝和鬼触。
通过原始事件观测、I2C 抓包、官方源码对比和显示初始化分段实验，将问题从 UI
层逐步收敛到显示输出工作状态及 ST7701 板级配置；对齐显示时序并替换庐山派
面板初始化序列后，原先异常的 DSI 图案测试恢复正常，再推进正常 UI 接入。**

### 当前结果边界

| 项目 | 截至本文的状态 |
| --- | --- |
| 软件输入链未启用、短点击丢失等问题 | 已修改，有日志或针对性测试支撑 |
| DSI 图案输出时的迟钝、鬼触 | 替换面板序列后，用户实板反馈正常；这是隔离实验结果 |
| 正常 UI 接入 | 已恢复业务入口、正常 VO 输出，并构建整卡候选；后续实板已有预览 IPC 往返日志，但不能代替完整触控验收 |
| 竖屏触控左右反向 | 已实现 X 轴反射，Docker 定向测试通过；最新增量尚未上板验证 |
| 完整 UI 长时间无鬼触、全部手势和不同负载 | 尚无完整验收记录，不能宣称永久稳定 |
| 摄像头预览黑屏 | 另一个正在排查的问题；预览命令及 bind 成功不等于视频画面正常 |

因此，“修复”在本文指已经找到有效的板级配置方案并通过对应隔离实验，
不代表整个项目的所有显示、媒体和触控功能均已完成最终验收。

## 2. 项目背景与为什么难

项目是基于庐山派 K230 的 Lawrec 双核音视频应用，使用 3.1 寸 480x800 竖屏。
Linux 小核运行 LVGL UI、网络和媒体业务，大核 RT-Smart 负责摄像头、显示及硬件媒体能力。
显示面板使用 ST7701；官方庐山派 RT-Smart 配置使用 CST128 触控适配。
本项目 Linux 实际绑定的是通用 `edt-ft5x06` 路径。

```text
输入路径：
触控 IC -> I2C + IRQ -> Linux edt-ft5x06 -> /dev/input/eventX
        -> evdev 解析/坐标映射 -> LVGL -> 页面事件

显示路径：
大核应用 -> kd_mpi_connector_init -> ST7701 内核驱动
        -> 像素时钟/PHY -> DSI/面板命令 -> VO 配置/输出 -> 屏幕

UI 叠加：
Linux LVGL -> DRM framebuffer/plane -> 共享显示硬件上的 UI 图层
```

难点不是代码量，而是**现象所在层与触发条件所在层不一致**：

- 表面看是 UI 触摸失灵，但异常已经出现在 Linux 原始输入事件中。
- 输入由 Linux 管理，主要显示初始化却在另一颗核的 RT-Smart 内核中完成。
- 正常 CanMV/Python 固件和 Linux 移植工程不是同一套底层链路，不能只照搬 Python 示例。
- 调用返回0、屏幕亮起、I2C 读成功都只是局部成功，不代表整个系统行为正确。
- 部分关键实现只有 SDK 静态库，需结合接口、源码和反汇编确认实际附带操作。
- 显示硬件状态可能在应用退出后保留，实验不冷启动就容易得到错误对照。

## 3. 如何发现：先把“触控不行”拆成不同问题

### 3.1 早期是输入接入和交付问题

工程最初主要通过 GPIO53 按键操作，触摸初始化曾被禁用。
排查发现 `main.c` 没有启用完整输入初始化，输入移植函数也曾是禁用后的空实现。
恢复 Linux evdev 到 LVGL pointer 注册后，又遇到“新 UI 已更新，触摸仍然 disabled”。

进一步检查发现，触摸移植代码位于动态库 `liblv_drivers.so`，板端只替换了 UI
可执行文件，仍加载旧驱动库。板端日志继续打印 `lv_port_indev disabled`。
同步配套动态库并修复打包遗漏后，日志确认触摸设备被打开、输入链被启用。

这类“没有响应”属于接入和部署问题，不能与后面的显示相关鬼触混为一谈。

### 3.2 再修复容易掩盖现象的输入解析问题

原读取循环一直读到 `EAGAIN` 才返回。如果一次读取中同时包含按下和松开，
最终状态就可能只剩 release，LVGL 看不到短点击。

修改为按 `SYN_REPORT` 分帧交付，用 `continue_reading` 继续处理下一帧，
保留完整的按下、移动、释放过程。本板优先使用驱动提供的 `ABS_X/Y + BTN_TOUCH`，
避免混用不同手指的多点坐标。补充 `SYN_DROPPED` 手势取消、等待释放，以及设备断开日志和重试。

这些是输入消费正确性修复，**不是通过过滤异常坐标掩盖鬼触**。

### 3.3 关键复现：显示前后，原始事件行为不同

用户观察到三个阶段：

| 设备状态 | 观察到的行为 | 初步判断 |
| --- | --- | --- |
| 重启后，不启动 UI 测试 evtest | 点按正常，没有鬼触 | 输入链不是始终失效 |
| 启动 UI 后 | evtest 持续上报坐标，触摸迟钝或界面无响应 | 异常不仅是页面点击逻辑 |
| 关闭 UI 后 | 偶尔仍有坐标事件 | 不能假设关闭进程就恢复了硬件状态 |

代表性的原始事件片段如下，摘自用户日志：

```text
Event: time 649.564728, type 3 (EV_ABS), code 54 (ABS_MT_POSITION_Y), value 176
Event: time 649.564728, type 3 (EV_ABS), code 1 (ABS_Y), value 176
Event: time 649.564728, -------------- SYN_REPORT ------------
```

一条坐标变化本身不能证明鬼触，必须同时确认是否有人接触、按下状态和释放是否完整。
随后实际采样中明确要求操作者松手，并把大小核是否运行作为实验条件记录。

**第一次重要判断：不能再只改 LVGL 映射，因为独立运行的 evtest 也观察到了异常。**
UI 与 evtest 各自拥有输入客户端队列，UI 消费慢并不意味着 evtest 必然消费慢。

## 4. 建立证据链：不是看到一个报错就改驱动

### 4.1 核对 Linux 运行配置

检查设备绑定、运行中的设备树、input 能力和中断计数，而不只看本地源码。
当时板端读取到：

| 项目 | 查到的配置或能力 | 不能由此推出的结论 |
| --- | --- | --- |
| compatible | `edt,edt-ft5306` | 不等于已读取芯片身份证明真实 IC 就是 FT5306 |
| 触控节点 | 当时为 `/dev/input/event0` | 换镜像后编号仍需重新核对 |
| 坐标范围 | X=0..479，Y=0..799，支持 BTN_TOUCH | 不证明物理坐标方向正确 |
| I2C clock-frequency | 配置400kHz | 不是示波器测量的总线频率 |
| IRQ | 下降沿，GPIO控制器局部offset=0 | 不能直接把全局GPIO23写成offset23 |
| RESET | 低有效 | 仍需结合驱动时序，不能只看极性 |

资料中出现过其它板型的引脚与触控示例，因此没有照抄其它板子的 GPIO 或更换驱动。

### 4.2 排除“必须由 UI 读取才触发”的解释

先确认大核确实启动，再做不运行 UI 的采样。大核初始化后、屏幕黑着且用户未触碰时，
一次10秒采样记录到触控 IRQ 增加597、evtest 坐标事件67帧。
禁用 UI 触摸读取的对照也没有消除异常。

这把判断从“UI 启动触发”推进到：**大核显示相关初始化已经能够使异常出现，
不要求 LVGL 正在消费触摸事件。**

这里的计数只是该次实验观察，不是正常中断频率，也不是修复后的性能指标。

### 4.3 用 I2C trace 看传输与触点数量

在一次异常采样中，通过内核 I2C tracepoint 记录到267个回复包，解析的触点数量均为1，
坐标约为(237,344)，传输返回2，表示两条 I2C 消息完成。
没有使用 `i2cget -f` 抢占正在工作的驱动总线。

这条证据说明：

- 这一轮并非单纯“Linux 保留旧槽位、芯片早已报告零触点”。
- I2C 事务完成不代表坐标一定对应真实接触，仍要看设备工作状态与原始数据。
- 也不能据此排除所有 I2C 电气问题，更不能直接宣称已经证明 MIPI 电磁干扰。

重新绑定触控驱动后，曾短暂恢复空闲和一次正常 DOWN/UP；再次运行 UI 后又出现持续按下。
因此没有把“每次打开 UI 就复位触控”当作永久修复。

## 5. 参考官方 Python：追到真实底层，而不是只看示例

同一硬件在官方 CanMV/Python 固件中触摸正确，这提供了一个有价值的参考，
但 Python 本身并不是让硬件自动正常的原因。沿调用链对比：

```text
Display.init(Display.ST7701, ...)
    -> modmedia.display.c -> kd_display_init_ex -> MPP connector/panel

machine.TOUCH(0)
    -> machine_touch.c -> drv_touch_reset

TOUCH.read()
    -> drv_touch_read -> CST128处理/公共触控层 -> Python结果
```

发现三类差异：

**初始化与复位。** 官方 TOUCH 构造会调用复位；如果示例先初始化显示再创建 TOUCH，
触控会在显示初始化之后复位。Linux `edt-ft5x06` 没有相应 input open/close 回调，
UI 打开 evdev 不会重新执行 probe 或 RESET，交换两个应用 init 调用并不等价。

根据当时核对的源码，Linux reset 是低有效逻辑下物理低5~6ms、拉高后等待300ms；
官方 CST128 默认有效值对应高20ms、低10ms、高50ms，另有不同路径的等待。
这些是源码推导，不是测过的板端波形，也没有直接抢占内核 GPIO 修改复位。

**触点协议。** 官方 CST128 按数量解析、检查范围，公共层会合成消失触点的 UP；
Linux 通用 FT 路径依赖记录的 event/id 管理槽位，存在差异。但 Linux 原本也是线程化 IRQ
读取 I2C，并非必须再额外增加线程。没有在缺少芯片和数据证据时全面重写通用 FT 驱动。

**显示适配。** 旧 SDK 使用的 ST7701 通用参数与庐山派专用时序、面板命令不同。
既然异常与显示工作状态相关，后续优先验证显示侧，而不是先调触摸 threshold/gain。

核对的官方源码版本和入口保存在
[初始化与 CanMV 链路对比](触控初始化与CanMV链路对比_2026-10-01.md)。
公开源码版本不自动等于用户实际使用的固件版本；后续提供的完整面板序列采用用户提供内容，
不能说每一条命令都在本机独立核实了官方出处。

用户提供的[庐山派触摸文档](https://wiki.lckfb.com/zh-hans/lushan-pi-k230/media/touch.html)
曾提示3.1寸屏适配中显示时钟会影响触摸读取。这是优先对比显示侧的线索，
不是本板已经测量到电磁干扰的证明，最终仍以受控实验和实际反馈判断。

## 6. 核心定位：把显示初始化逐段拆开

### 6.1 从整个工程缩成 connector-only 实验

用户另一轮测试反馈，单独执行 power/reset/backlight 正常，调用 connector init 后异常。
于是保留大核最小测试入口，仅初始化 connector 并提供约60秒观察窗口，
不运行摄像头、AI、RTSP、录像或正常 UI 业务，Linux 侧独立观察 evtest。

继续拆解的主链如下：

```text
connector power/reset
    -> pixclk + command buffer + PHY
    -> DSI配置 + 面板命令 + DSI使能
    -> VO init + VTTH + VO参数
    -> VO enable：提交配置，并调用时间戳操作
```

这里讨论的是 **MIPI DSI/PHY、VO 像素时钟与显示输出**。
MAPI 是软件媒体接口层，不是另一个叫“MAPI 时钟”的硬件时钟。

### 6.2 实验结果总表

| 阶段 | 本轮隔离方式 | 已有反馈或观察 | 能得到的结论 |
| --- | --- | --- | --- |
| 上电/复位/背光 | 不调用 connector init | 用户反馈正常 | 继续拆 connector；该组来自另一轮用户反馈 |
| CLOCK_PHY_ONLY | 执行时钟/命令缓冲/PHY，跳过DSI、面板和VO | 用户反馈正常，看到内核新标记 | 仅配置这些操作不足以复现；不能排除实际传输时的时钟影响 |
| DSI_PANEL_ONLY | 加入DSI配置与面板初始化，跳过VO | 用户反馈正常 | 继续检查VO使配置生效后的状态 |
| VO_ENABLED_VTTH_OFF | 完整输出，仅请求关闭VTTH | 仍迟钝、鬼触 | 关闭请求不足以改善；不等于全程没有VTTH中断 |
| VO_CONFIG_ONLY | 保留VO初始化/参数，跳过最后enable | 用户反馈正常 | 关键触发边界缩到enable或其生效后的状态 |
| TIMESTAMP_ONLY | 单独调用时间戳，仍不执行VO enable | 用户反馈正常 | 此单独调用不足以触发，仍不排除组合影响 |
| DSI_PATTERN_ON | 内核仍跳过VO enable，应用启用DSI内部图案 | 图案可见，同时仍迟钝、鬼触 | 不依赖正常VO视频输出也能复现，重点转向显示传输、面板扫描与配置 |
| 27MHz时序组 | 同一诊断内核，只替换整组应用参数 | 用户反馈改善，仍偶发鬼触 | 显示参数参与影响，但时钟并不是已确认的唯一因素 |
| 24.75MHz时序组 | 独立候选参数，未叠加面板修改 | 已编译/同步，未取得明确板测结果 | 不能写成失败或成功，也不能称为最终方案 |
| PHY两lane组 | 修改内核硬编码，复用24.75MHz应用 | 已构建，未取得明确板测结果；后来恢复四lane | 不能把lane数称作已证实根因 |
| LCKFB面板序列组 | 恢复27MHz/四lane，仅替换面板函数体 | 用户反馈这组正常 | 支持板级面板初始化适配是关键改善因素，尚未定位具体寄存器或电气机制 |

面试不必背全部实验名称，记住这条主线即可：
**输入原始层确认异常 -> connector分段 -> enable附带操作拆分 -> DSI图案复现 -> 时序及面板适配。**

### 6.3 为什么需要反汇编 SDK 库

本地 `libvo.a` 核对揭示了三个容易误判的地方：

- `vo_init()` 内部先开启过 VTTH，外层后来请求关闭，不能证明初始化全程无中断。
- VO enable 不只是“打开显示”，还提交配置并调用 `kd_vo_timestamp_enable()`，需拆开验证。
- 本地 DSI enable 实现没有把传入的开关值用于真正的关闭分支，所以不能用
  `dsi_enable(0)` 作为有效的“关闭 DSI”对照。

这些发现让实验依据从函数名转向实际行为，避免得到看似合理但前提无效的结论。

### 6.4 为什么 DSI 图案实验是关键转折

图案由 DSI 内部测试路径生成，不需要正常摄像头帧或正常 VO enable。
实板同时确认“有图案”和“触控异常”，证明问题可以在更小的输出路径复现。

它使摄像头、AI、业务 IPC 和 UI 页面逻辑不再是复现的必要条件。
但它仍不能区分串扰、供电、面板扫描、时序及协议耦合等具体机制，
不能把“开始显示后异常”直接写成“已用示波器确认 MIPI 电磁干扰”。

## 7. 修复方案：整组显示参数 + 板级面板序列

### 7.1 对齐可生成的像素时钟与行场参数

旧 SDK 表中使用约39.6MHz配置；参考的新版庐山派配置请求27.561MHz，
本工程按594MHz父时钟和分频编码选择可表达的27MHz配置：

```text
594000 kHz / (21 + 1) = 27000 kHz
名义刷新率 = 27000000 / (528 × 870) ≈ 58.78 Hz
```

以上是按配置模型推算，不是板端PLL或波形实测；枚举名中的30FPS也不是刷新率测量。
最终保留的应用参数位于 `big/main.cc` 的 `sample_connector_init()`：

```cpp
connector_info.pixclk_div = 21;
connector_info.phy_attr.n = 3;
connector_info.phy_attr.m = 52;
connector_info.phy_attr.voc = 0x1f;
connector_info.phy_attr.hs_freq = 0xb5;
connector_info.resolution.pclk = 27000;
connector_info.resolution.phyclk = 324000;
connector_info.resolution.htotal = 528;
connector_info.resolution.hdisplay = 480;
connector_info.resolution.hsync_len = 8;
connector_info.resolution.hback_porch = 10;
connector_info.resolution.hfront_porch = 30;
connector_info.resolution.vtotal = 870;
connector_info.resolution.vdisplay = 800;
connector_info.resolution.vsync_len = 10;
connector_info.resolution.vback_porch = 20;
connector_info.resolution.vfront_porch = 40;
```

27MHz组仍有偶发鬼触，所以没有停在“降频了就算修好”。
24.75MHz候选同时改变PHY与消隐区，其名义刷新率约40.76Hz，也不是只降低了8.3%的频率。
没有结果记录的候选不用于支持最终归因。

### 7.2 冻结其它变量，只替换面板初始化

按最后确认的测试边界，固定27MHz/324Mbps、PHY参数和原 `K_DSI_4LAN`，
DSI/VO测试逻辑保持不变，仅替换 SDK 下：

```text
src/big/mpp/kernel/connector/src/st7701.c
    st7701_480x800_init(k_u8 test_mode_en)
```

使用用户提供的新版 LCKFB 专用面板完整命令和延时序列。
不能只替换几个显眼寄存器，因为分页、gamma、供电/GIP相关配置和命令顺序都存在差异。

几处代表性差异如下，仅用于解释适配范围，不是已证明单个寄存器的根因：

| 面板page 0x10命令 | 旧通用序列 | 替换后的LCKFB序列 |
| --- | --- | --- |
| C1 | `10 02` | `04 02` |
| C2 | `31 02` | `37 08` |
| CC | `10` | `38` |

完整函数体以 SDK 当前源码和面板测试归档为准。序列包含soft reset、sleep out、
分页配置、gamma/GIP等命令、pixel format以及display on，并保留用户提供的延时。
命令体与延时作为一组修改，因此结果不能再细分为“必然是某一个寄存器”。

**用户随后反馈这组正常。** 在27MHz/四lane的既定条件下，仅替换面板函数体后，
之前异常的图案实验恢复正常，这是本次修复最有价值的结果。

工程层面可以归纳为：**旧SDK通用ST7701初始化与当前庐山派屏幕的板级适配不足，
需要使用匹配的显示工作点和面板初始化序列。**
物理层面究竟是哪条命令、何种扫描或耦合导致异常，现有证据没有完全回答。

### 7.3 恢复正常 UI，不保留诊断早退

隔离测试正常后，恢复大核业务入口、正常 VO enable 和 VTTH=1，
关闭 `dsi_test_mode`、`screen_test_mode`，移除connector-only的60秒诊断早退和独立时间戳调用。
保持已通过的时钟、PHY、四lane及面板命令体，Linux触控驱动和阈值不改。

后续竖屏实板反馈左右映射反向，这是独立的坐标问题，不是鬼触回归的充分证据。
在480x800归一化后使用已有反射模式：

```text
x_ui = 479 - x_normalized
y_ui = y_normalized
```

当前调用在 `little/src/ui/lvgl_port/k230/lv_port_disp.cpp`，公式实现位于
`lv_port_indev.c`。已测试左右端点、中心及按下/释放，不修改触控IC阈值。
此最新修正仍需上板验收，部署必须包含 `liblv_drivers.so`。

## 8. 保证“测到的确实是改过的版本”

这次排查也遇到了构建和交付陷阱，处理它们是证据闭环的一部分。

| 陷阱 | 实际处理 | 经验 |
| --- | --- | --- |
| 新UI加载旧输入库 | 配套同步UI、LVGL与liblv_drivers，修复打包遗漏 | 可执行文件更新不等于全部代码更新 |
| 修改st7701.c后只换应用ELF | 用Docker重建MPP内核及大核启动固件 | 先确认代码属于应用、动态库还是内核 |
| ELF加载失败被误认成显示故障 | 比较文件大小和SHA256，发现传输不完整；临时文件上传、校验后替换 | 先证明程序实际执行，再讨论初始化结果 |
| ROMFS仍内嵌旧大核应用 | 明确重新生成romfs.c，检查完整当前ELF字节存在于RTT payload | staging目录里的文件不代表最终镜像里的文件 |
| 上一轮显示状态残留 | 每组完整断电上电，先观察基线，再启动测试 | 应用退出不保证硬件复位 |
| 应用打印旧测试名 | 用实际内核标记、参数及校验和确认阶段 | 提示字符串不等于当前执行路径 |

首次 DSI 图案 ELF 加载失败时，板端文件为9,240,576字节、本地应为11,812,152字节，
SHA256不一致；重新传输核对后解决。没有把 `lwp load faild` 当作DSI执行失败。

所有编译均通过项目Docker入口。应用参数测试用 `bash tools/build.sh big`；
内核分段测试用对应 `touch-*` 目标；正常双核/整卡集成用 `bash tools/build.sh touch-ui`。
诊断产物单独归档，保存源码、标识、日志和SHA256，不与正常发布版本混用。

## 9. 最终结论与复盘

本次不是一个单独的“坐标公式写错”，而是三个层次的问题叠在一起：

1. **软件接入层：** 输入曾禁用、动态库漏同步、短按分帧不正确，让触控表现为无响应。
2. **板级适配层：** 显示输出条件下的触控异常可独立复现；显示时序改善现象，
   完整LCKFB面板序列使对应隔离实验恢复正常，是关键修复路径。
3. **UI方向层：** 恢复竖屏UI后左右反向，采用X轴反射单独修正，仍待新版本实板验证。

最重要的收获是：**先确认异常从哪一层开始，再改变那一层附近的变量；
不要把应用症状当作根因，不要把“返回成功”当作验收成功。**

还需要完成正常VO/UI下的长时间空闲、中央和四角、短点按/拖动/释放，以及业务负载验收。
摄像头黑屏需独立检查帧输出和图层状态，不再通过盲目修改触控参数解决。

## 10. 面试表达

### 10.1 推荐题目

**“K230双核系统中，显示输出引发的触控异常定位与板级适配。”**

相比“我修过一个触摸驱动bug”，这个题目更准确，也更能体现跨层定位能力。

### 10.2 约两分钟回答

> 我在开发K230双核音视频项目时，遇到过一个比较难的触控问题。Linux小核负责
> LVGL界面，大核负责显示和摄像头。触控单独用evtest测试是正常的，但一启动显示
> 相关程序，就出现触摸迟钝、无人接触也上报坐标的问题。最开始看起来像UI映射或
> I2C驱动错误，但它跨了两个操作系统，定位比较困难。
>
> 我先把软件接入问题处理掉，包括旧动态库没有同步、短点击按下和释放被合并。
> 然后不再只看界面是否响应，而是看原始输入事件、中断计数和I2C数据。
> 当我确认不运行UI、只初始化大核显示也会产生异常，并且异常时芯片读数仍报告
> 触点，排查方向就从LVGL转到了显示侧。
>
> 接着我参考官方CanMV源码，把connector初始化拆成时钟/PHY、DSI/面板、VO配置
> 和最终enable几段，每轮冷启动，只改变一个阶段。因为部分实现只有静态库，
> 我还核对了反汇编，发现VO enable包含时间戳操作，就把它也单独测试。
> 最关键的是：不启用正常VO输出，只用DSI内部测试图案也能复现。这说明摄像头和
> UI业务都不是必要触发条件，应该重点查显示传输状态和面板适配。
>
> 最后对齐庐山派显示参数，发现只调整到27MHz虽然改善，但还会偶发。保持这组
> 参数和其它测试条件不变，替换为LCKFB专用ST7701面板初始化序列后，原先异常的
> 图案测试恢复正常。之后恢复正常UI，并把竖屏左右反向作为独立映射问题处理。
>
> 这件事让我认识到，嵌入式问题不能只在报错的模块里找原因。更重要的是建立最小
> 复现、逐步缩小触发条件，并验证实际固件版本。当前隔离实验已经验证方案有效，
> 正常UI的长时间稳定性和最新映射修正还需要继续实板验收。

这段最后一句按真实验收进度更新；没有新增实板证据时不要删掉边界说明。

### 10.4 面试追问与回答要点

**问：为什么你能判断不是单纯的LVGL问题？**

因为独立evtest也能看到异常，而且大核初始化后、不运行UI仍有无人接触的事件。
这排除了“只有LVGL坐标转换错误”作为完整解释，不是宣称LVGL完全没有其它问题。

**问：为什么不先加防抖或过滤小幅坐标变化？**

因为错误触点可能持续且在合法范围内，过滤抖动无法判断触点是否真实，反而会掩盖问题、
吞正常短按或释放。先修事件分帧等消费正确性，再用原始数据定位异常来源。

**问：I2C读成功，为什么触摸还会错？**

事务成功只是传输层完成，读到的触点不一定对应真实接触。需要同时检查触点数量、
原始记录、input状态和设备工作条件；不能仅凭返回值认定I2C、芯片和环境都没问题。

**问：你最后证明是MIPI电磁干扰了吗？**

没有直接测量证明。证据支持异常与显示输出及面板配置相关，板级配置修改有效。
具体电磁耦合、供电或面板扫描机制，还需要波形、时钟或更细的寄存器对照。
工程修复点和物理机理确认是两个层次。

**问：27MHz为什么不是直接填官方27.561MHz？**

按照当前SDK的594MHz父时钟与整数分频模型，divider21对应除22，得到27MHz。
选择能表达的工作点并对齐整组行场和PHY参数；这个计算不是实际时钟测量。

**问：换了多个时序参数，算不算单一变量？**

时序组是整组候选A/B，不是逐个寄存器的归因实验，改善不能单独归到降频。
后面的面板测试冻结时序和lane，仅替换函数体；它进一步收敛到命令及延时这一组。

**问：为什么最终仍保留四lane？**

应用DSI lane和PHY lane是不同入口。曾建立两lane候选，但没有完整板测结论，
不能认定其解决或导致问题。最终按确认的测试边界恢复四lane，以冻结其它变量验证面板序列。
这不等于证明四lane是所有屏幕的规范配置。

**问：如何避免测到旧代码？**

确认修改所在的应用/动态库/内核层，配套更新；核对SHA256和实际内核标记；
对ROMFS还检查最终RTT payload内的完整ELF字节，不只检查源码或staging目录。

**问：你的方案现在能直接称为完整解决了吗？**

可以说“找到了有效板级方案，对应隔离实验已正常并推进UI接入”。
还不能说“所有场景长期稳定、项目已全部验收”，尤其最新方向修正尚未上板。

# lawrec 工程实现说明

## 1. 工程定位

`lawrec` 当前是一个运行在 K230 小核 Linux 侧的业务工程，围绕“主界面、预览页、按键操作、RTSP 控制、大小核协同”这几条主线展开。

从职责划分看：

- 小核 Linux 负责：
  - LVGL UI
  - GPIO53 按键输入
  - 本地 RTSP 生命周期控制
  - 向大核发送预览相关 IPC 指令
- 大核 RT-Smart 负责：
  - 摄像头/预览链路
  - 编码基础能力
  - AI 与显示侧业务

当前工程已经收敛成“预览走大小核 IPC，RTSP 走小核本地控制”的结构。

## 2. 目录结构

核心代码位于：

- `src/little/buildroot-ext/package/lawrec/src/ui`
- `src/little/buildroot-ext/package/lawrec/src/service`
- `src/little/buildroot-ext/package/lawrec/src/control`
- `src/little/buildroot-ext/package/lawrec/src/rtsp`
- `src/little/buildroot-ext/package/lawrec/src/common`

模块职责如下：

- `ui/`
  - 页面、输入、消息分发、大小核 IPC 接入
- `service/`
  - 本地 Unix Socket 服务入口
- `control/`
  - 小核统一状态机
- `rtsp/`
  - live555 + MAPI 推流实现
- `common/`
  - UI/service/control 共用协议

## 3. 当前主控制链

当前工程最重要的逻辑链是：

1. 用户在小核 UI 上操作
2. UI 决定是发给大核 IPC，还是走本地 RTSP 控制
3. 预览请求通过 `door_lock` IPC 发给大核
4. RTSP 请求在小核本地进入 `lawrec_control`
5. `lawrec_control` 决定是否允许启动/停止 RTSP
6. RTSP 模块通过 MAPI + live555 提供推流能力

一句话概括：

**预览由大小核配合完成，RTSP 由小核本地控制，但 RTSP 的前提是大核预览链已经就绪。**

## 4. UI 主循环

入口在：

- `src/little/buildroot-ext/package/lawrec/src/ui/src/main.c`

启动顺序如下：

1. 设置 malloc 行为
2. 把 stdout/stderr 重定向到统一日志文件
3. 初始化 `lawrec_control`
4. 初始化 LVGL
5. 初始化 DRM 显示
6. 创建主页面
7. 初始化按键
8. 初始化消息系统 `msg_proc`
9. 进入 UI 主循环

主循环只做三件事：

- `lv_timer_handler()`
- `lawrec_key_poll()`
- `ui_msg_proc()`

这里的设计原则是：

- UI 线程不自己做复杂阻塞逻辑
- 后台线程把异步结果投递到消息队列
- 统一在 UI 线程里更新控件

## 5. 按键输入逻辑

代码位于：

- `src/little/buildroot-ext/package/lawrec/src/ui/src/key_proc.c`

当前按键使用 GPIO character device 事件监听方式：

- 监听 `gpio53`
- 短按切换焦点
- 长按激活当前控件

这套输入方案不依赖旧的触控链路，适合当前“按键为主”的交互方式。

## 6. 页面逻辑

### 6.1 主页面

主页面代码在：

- `src/little/buildroot-ext/package/lawrec/src/ui/src/scr_main.c`

它负责：

- 绘制主面板
- 展示设备状态
- 作为功能入口页

当前“进入拍摄”入口会切到预览页。

### 6.2 预览页面

预览页面代码在：

- `src/little/buildroot-ext/package/lawrec/src/ui/src/scr_preview.c`

当前预览页做了两件关键事情：

1. 进入页面时，只发 `MSG_CMD_PREVIEW_ENTER`
2. RTSP 由单独按钮控制，不再自动跟随页面进入时直接开启

这是当前实现里很重要的收敛：

- 预览页进入 != 自动 RTSP 启动
- 预览链先起来
- RTSP 在预览 ready 后再由用户主动切换

预览页的 RTSP 按钮状态有 5 种：

- `UNAVAILABLE`
- `IDLE`
- `STARTING`
- `LIVE`
- `STOPPING`

这些按钮状态不是 UI 自己猜的，而是从 `lawrec_control` 读取的。

## 7. `msg_proc`：大小核 IPC 和本地消息总线

代码位于：

- `src/little/buildroot-ext/package/lawrec/src/ui/src/msg_proc.cpp`

它是当前工程的消息中枢。

### 7.1 两条消息路径

当前存在两条并行路径：

- 大核 IPC 路径
  - `PREVIEW_ENTER`
  - `PREVIEW_EXIT`
  - `PING`
  - 以及大核返回结果
- 小核本地路径
  - `RTSP_START`
  - `RTSP_STOP`
  - `RTSP_QUERY`

这里的关键点是：

**RTSP 不再走大核 IPC。**

原因是：

- RTSP server 在小核 Linux
- RTSP 生命周期本质上是小核本地事务
- 如果再绕大核转发，链路会更复杂，也更难调试

### 7.2 `msg_send_data()` 的设计

`msg_send_data()` 先判断命令是不是本地 RTSP 命令：

- 如果是，就直接进入 `lawrec_control`
- 如果不是，再发给大核 IPC

所以当前逻辑是：

- 预览命令发大核
- RTSP 命令留小核

### 7.3 IPC 线程

`thread_ipcmsg()` 会：

1. 等待 `/dev/ipcm_user` 可用
2. 连接大核服务 `door_lock`
3. 发送 `PING`
4. 进入 `kd_ipcmsg_run()`

当前代码还做了一个兼容处理：

- 优先尝试创建实时调度线程
- 如果失败，就回退为普通 detached 线程

这样能避免某些板端环境下 IPC 线程直接创建失败，导致 UI 看起来正常但大小核 IPC 实际没跑起来。

### 7.4 UI 消息队列

无论消息来自：

- 大核 IPC 回包
- 本地 RTSP 控制结果
- 本地状态同步线程

最终都会进入 `ui_msg_t` 队列，再由 `ui_msg_proc()` 串行消费。

这样做的目的很明确：

- 后台线程不直接操作 LVGL
- UI 更新时序收敛到单线程
- 避免状态分散在多个回调里

## 8. `lawrec_control`：小核统一状态机

代码位于：

- `src/little/buildroot-ext/package/lawrec/src/control/src/lawrec_control.cpp`

这是当前工程最重要的状态收敛模块。

它保存三类状态：

- `g_preview_requested`
  - UI 是否已经发出预览请求
- `g_preview_active`
  - 大核是否确认预览真正已就绪
- `g_rtsp_enabled`
  - 用户侧是否期望 RTSP 处于开启状态

同时它还会读取 RTSP worker 的实时状态：

- `IDLE`
- `STARTING`
- `LIVE`
- `STOPPING`
- `FAILED`

### 8.1 为什么要做这层

因为当前有 3 个角色都依赖同一组状态：

- UI
- 本地 service
- RTSP worker

如果每层都自己维护一份状态，会非常容易失真：

- preview 已经关了，但 RTSP 按钮还显示可用
- RTSP 已经失败，但 UI 还显示直播中
- service 以为 preview ready，其实大核没有真的打开

因此 `lawrec_control` 被设计成统一入口。

### 8.2 当前约束

当前工程明确限制：

- preview 未 active 时，不允许启动 RTSP
- preview 关闭时，RTSP 必须同步被拉停
- RTSP stop 是幂等的，可重复调用

这决定了当前工程的运行关系：

**preview 是 RTSP 的前置条件。**

## 9. `service`：本地控制入口

代码位于：

- `src/little/buildroot-ext/package/lawrec/src/service/src/main.cpp`

`lawrec_service` 当前作用很明确：

- 在小核创建 Unix Socket：
  - `/var/run/lawrec-service.sock`
- 接收本地请求
- 转发到 `lawrec_control`
- 返回结果和 RTSP 状态

当前 service 只暴露三种命令：

- `RTSP_START`
- `RTSP_STOP`
- `RTSP_QUERY`

它是一个“薄服务”：

- 不自己重复做业务状态机
- 不在 service 里额外复制 UI 逻辑
- 只做进程级入口与调度

## 10. RTSP 当前实现

代码位于：

- `src/little/buildroot-ext/package/lawrec/src/rtsp/main.cpp`
- `src/little/buildroot-ext/package/lawrec/src/rtsp/src/streaming_player.cpp`

RTSP 模块当前负责：

- 初始化 live555 RTSP server
- 初始化 MAPI 系统
- 配置 VICAP / VENC / AENC
- 接收编码回调
- 把音视频数据送入 live555 source/session

它不负责：

- UI 页面
- 按键输入
- 大核 IPC
- 预览页面状态机

这意味着 RTSP 模块本身是媒体层，不是页面层。

## 11. 当前的实现逻辑总结

当前 `lawrec` 的实际逻辑可以总结为：

1. 小核 UI 负责展示与交互
2. 预览请求通过 IPC 发给大核
3. 大核返回 preview 结果
4. `lawrec_control` 根据 preview 状态决定 RTSP 是否可用
5. 用户点击 RTSP 按钮后，小核本地启动或停止 RTSP
6. UI 通过本地状态同步线程刷新按钮与状态文本

也就是说，现在不是把所有逻辑都塞进 UI，而是：

- UI：交互层
- msg_proc：消息桥接层
- control：状态收敛层
- service：本地服务入口
- rtsp：媒体实现层

这个边界已经比较适合后续继续扩展，比如：

- 录像
- 码率配置
- 网络设置
- 直播状态展示

## 12. 当前工程建议的理解方式

如果后续有人继续接手这个工程，推荐按下面顺序理解：

1. 先看 `ui/src/main.c`
2. 再看 `ui/src/scr_main.c` 和 `ui/src/scr_preview.c`
3. 再看 `ui/src/msg_proc.cpp`
4. 再看 `control/src/lawrec_control.cpp`
5. 最后看 `service/src/main.cpp` 和 `rtsp/src/streaming_player.cpp`

因为当前工程真正的骨架不是单个页面，而是：

**UI -> msg_proc -> control -> service/rtsp + big-core IPC**

理解这条链路之后，后续扩展功能会顺很多。

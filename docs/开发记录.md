### xiaodemo 的目的

`xiaodemo` 只做 4 件事：

1. 复用当前已经跑通的 little `lawrec/ui/lvgl_port`
2. 直接显示当前触点坐标
3. 在屏上画出拖动轨迹
4. 提供 4 个按钮快速切换/验证输入映射：
   - `normal`
   - `flip-x`
   - `legacy`
   - `clear`

这样上板后可以直接判断：

- 原始 event 坐标是否稳定
- 是否存在松手不释放
- 是否存在左右翻转

### 一、显示链问题总结

#### 1. 预览只显示一半、画面乱码

这类问题一开始很容易误以为是：

- 屏幕初始化错误
- 旋转方向错误
- OSD 叠加错误

但实际排查后确认，根因并不止一处，而是多个配置叠加：

1. `lckfb` 板型本身是：
   - `ST7701_V1_MIPI_2LAN_480X800_30FPS`
2. 旋转模式必须走：
   - `K_ROTATION_90`
3. chn0 的显示输出尺寸必须匹配：
   - `800x480`
4. `vi_vo.h` 里的 `ISP_CHN0_WIDTH/HEIGHT`
   - `osd_width/osd_height`
   必须与旋转后的显示链严格对应
5. `sample_vo_thread`、layer act size、OSD size 只要有一处尺寸还停留在 `1080x1920` 旧配置，就会直接表现为：
   - 只显示半屏
   - 叠加错位
   - 花屏/乱码

最终稳定结论：

- `lckfb` 下必须把整套显示尺寸统一为：
  - 视频层输入：`800x480`
  - OSD 缓冲：`480x800`
  - 显示旋转：`K_ROTATION_90`

#### 2. 蓝框和白框重叠

现象：

- 屏幕上同时出现一层蓝色框和一层白色框

根因：

- 程序同时启用了两套画框路径：
  1. `kd_mpi_vo_draw_frame()` 的 VO 线框
  2. OSD 上用 OpenCV 画的 ARGB 白框

这在横屏 sample 里不一定明显，但在 `lckfb` 旋转屏下会非常突兀。

最终处理：

- `lckfb` 下关闭 `VO draw_frame` 线框
- 只保留 `OSD` 框和关键点

经验：

- 以后在 `lckfb` 路径，默认只保留一套框
- 如果需要调试映射，可以临时开 `VO draw_frame`，但不要和 OSD 常驻同时启用

#### 3. OSD 小框看起来“不显示”

这是本轮最隐蔽的一个显示问题。

现象：

- 远处小脸日志里可能已经有框
- 但屏幕上看不到任何东西

根因：

- `map_detect_box_to_osd()` 之前使用的是整型除法
- 小框在从 `1280x720` 缩放到 `480x800` OSD 时，宽或高可能直接被截断成：
  - `0`
  - `1`

表现上就像：

- 明明检测到了，但没有画出来

最终处理：

1. OSD 缩放改成全浮点计算
2. 对缩放后宽高增加最小绘制保护：
   - 大于 0 且小于 2 像素时，强制拉到 2 像素

经验：

- 小目标在旋转屏上的可视化，不能用纯整型缩放
- 后续任何 OSD 映射代码都优先保留浮点，到最终绘制前再取整

### 二、模型推理链问题总结

#### 1. 最早阶段的“满屏乱框 / NaN / 2147483647”

曾经的典型日志：

- `raw_box0 non-finite`
- `box0=(2147483647,2147483367)-...`
- `detect boxes=1434`

这类现象非常关键，它说明：

- 不是 OSD 错
- 不是框映射错
- 不是 draw_frame 错
- 而是 `retinaface decode` 上游就已经坏了

最终确认：

- 当前工程里 `RVV` 路径在板端会产生异常值
- 切到标量路径后，坏值问题消失

结论：

- `lawrec` 当前必须固定：
  - `ENABLE_RVV 0`
- 在未重新验证前，不要恢复 `RVV`

#### 2. `retinaface` 输入 pad 方向问题

这是检测链能否正常工作的核心问题之一。

现象经历过三个阶段：

1. pad 错时：
   - 满屏乱框
   - `NaN/Inf`
2. 换成另一种硬编码 pad 后：
   - 稳定 0 框
3. 改为按输入/输出尺寸动态计算 pad 后：
   - 才恢复出合理框

最终结论：

- `1280x720 -> 320x320` 时，本质上是：
  - 宽度先缩到 `320`
  - 高度缩到 `180`
  - 上下各 pad `70`
- 但不应该继续依赖板型宏去硬编码 `70`
- 最稳妥的方式是：
  - 用 `input_shape(0)` 读取模型真实输入尺寸
  - 动态计算 `h_pad_before/h_pad_after`
  - 动态计算 `w_pad_before/w_pad_after`

经验：

- 以后模型输入尺寸、板型或采集尺寸一旦变化，优先保留“动态 pad”写法
- 不要再依赖“某个板子应该走某个硬编码 pad 分支”的经验式写法

#### 3. `Model` 输入 shape 获取链必须与 sample 对齐

曾经 `lawrec` 比 sample 少了：

- `input_shape(size_t idx)`

这导致 `MobileRetinaface` 只能退回：

- `ai2d_out_tensor_.shape()`

这种写法虽然能编译，但并不等价于 sample 的真实输入定义链。

最终修复：

- 在 `model.h/model.cc` 中补回 `input_shape()`
- `mobile_retinaface.cc` 恢复为 sample 同款：
  - `auto out_shape = input_shape(0);`

经验：

- `Model` 基类不要随意裁接口
- 尤其是 `input_shape/output_shape` 这类和 ai2d 强相关的接口

#### 4. 检测阈值并不是一次就能定死

本轮实际经历过的阈值变化：

1. `0.60`
   - 近脸能出框
   - 远脸大量漏检
   - 临界帧一闪一闪
2. `0.50`
   - 稳定性略好
   - 远脸仍不够
3. `0.35`
   - 远脸显示显著改善

注意：

- 这不表示 `0.35` 一定是最终业务最优值
- 只是本轮在“尽量让远近都能显示框”这一目标下更合适

经验：

- 检测阈值必须结合实际板端镜头、距离、显示需求来定
- 如果后续误检增多，优先引入“时序稳定”或“滞回”机制
- 不要第一反应又回去加尺寸硬过滤

#### 5. “远处小脸不显示”至少有三层可能

这次已经实战验证过，远处小脸不显示并不只是一种原因，至少可能来自：

1. `obj_threshold_` 太高
2. 业务层最小框过滤
3. OSD 缩放被整型截断成 0 像素

因此以后遇到“小脸不显示”时，排查顺序建议固定为：

1. 看 `conf_max`
2. 看 `detect boxes`
3. 看 `draw boxes`
4. 再看最终屏幕效果

不要再只改某一个环节就下结论。

### 三、采集链和 sample 对齐注意事项

#### 1. `chn1` 必须走 sample 的稳定组合

本轮已经验证，下面这个组合是稳定的：

- `chn1.pix_format = PIXEL_FORMAT_RGB_888_PLANAR`
- `kd_mpi_vicap_dump_frame(..., VICAP_DUMP_YUV, ...)`
- `kd_mpi_vicap_set_database_parse_mode(..., VICAP_DATABASE_PARSE_XML_JSON)`

此前偏离 sample 的几种改法会导致：

- `dump_frame failed`
- `chn1` 无法正常拿到模型输入
- 或者 ISP 数据解释错误

经验：

- 以后如果推理链异常，先回看这三项是否被改偏
- 不要轻易把 `RGB dump`、`HEADER parse` 当成默认更优方案

#### 2. `lawrec` 与 `doorlock` 的喂数方式不同

`doorlock` 原始大核路径里，曾经有一段做法是：

1. `kd_mpi_sys_mmap_cached()`
2. `memcpy()` 到自己申请的 `vaddr/paddr`
3. 再把 `vaddr/paddr` 喂给 `retinaface`

而 `lawrec` 当前主路径采用的是：

1. 直接 `mmap` dump frame
2. 直接喂给 `retinaface`

本轮最终是直接喂数链打通了，没有再回退到 doorlock 的整帧 copy 模式。

经验：

- 如果后续再出现“模型输入似乎不稳定”的异常，可以把“doorlock 复制一份再跑”的策略作为保底对照项
- 但当前版本不需要为了稳定性强行退回整帧 copy

### 四、启动、退出和系统稳定性问题

#### 1. `q` 退出不可靠并不是编译错

本轮早期出现过：

- 输入 `q` 没反应
- `Ctrl+C` 后线程异常
- `stack overflow`

最终确认：

- 这更多是 RT-Smart 自启动场景下 `getchar()`/终端读取方式的问题
- 不是单纯“程序没编对”

最后稳定方案是：

- 优先读 `/dev/tty`
- 回退再用 `getchar()`
- `SIGINT` 时显式把 `app_run = false`

经验：

- 以后自启动 app 的退出线程，默认优先 `/dev/tty`
- 不要直接照抄桌面 Linux 上的阻塞输入写法

#### 2. 板端曾出现 page fault / illegal instruction / stack overflow

这些报错在本轮都真实出现过，但根因不完全相同：

1. 一部分来自：
   - 推理链读到了坏数据
2. 一部分来自：
   - 输入/退出线程状态混乱
3. 一部分来自：
   - `RVV` 路径或错误配置触发的异常行为

结论：

- 板端一旦出现 fault，不要先怀疑“用户没烧进去”
- 先看：
  - build tag
  - 输入链
  - decode 是否有 NaN
  - 是否走了错误分支

### 五、构建和烧录链注意事项

#### 1. 最重要的坑：`lawrec.elf` 不等于板子实际运行的 `fastboot_app.elf`

本轮反复确认过：

- `make lawrec` 只会产出：
  - `src/reference/business_poc/lawrec/big/out/lawrec.elf`
- 但真正会被打进 ROMFS、随系统启动的是：
  - `src/big/rt-smart/userapps/root/bin/fastboot_app.elf`

后来已经修成：

- `make lawrec` 完成后自动覆盖 `fastboot_app.elf`

经验：

- 以后只要板端日志和源码对不上，先查：
  - `strings lawrec.elf`
  - `strings fastboot_app.elf`
  - 两者 md5 是否一致

#### 2. 改了大核 app 后，必须重新走完整 ROMFS 打包链

真正可靠的顺序是：

1. `make CONF=k230_canmv_lckfb_defconfig lawrec`
2. `make CONF=k230_canmv_lckfb_defconfig rt-smart-apps`
3. `make CONF=k230_canmv_lckfb_defconfig rtt_update_romfs`
4. `make CONF=k230_canmv_lckfb_defconfig big-core-opensbi`
5. `make CONF=k230_canmv_lckfb_defconfig build-image`

经验：

- 改了 app、本地模型、启动脚本、ROMFS 内容后，不要省略 `rt-smart-apps`
- 只跑 `rtt_update_romfs` 不够

#### 3. 优先只刷 RTT 分区

本轮实际联调已经验证：

- 大部分大核问题只需要更新：
  - `rtt_system.bin`

这样有两个好处：

1. 联调速度快
2. 避免整卡重烧带来小核/rootfs 干扰

经验：

- 除非涉及小核、rootfs、分区布局，否则优先只刷 RTT

#### 1. 当前版本适合作为新的稳定基线

当前建议把以下版本作为“lckfb 大核显示 + 检测 + OSD”的新稳定基线：

这会直接造成两种现象：

- 点一下后仍然保持按下，表现为“没点也像在点击”
- 坐标流还在更新，但状态流没有同步释放，导致误触发

### 2. 本轮触控收敛方案

最终在 `lawrec` little UI 中固定以下规则：

- 继续使用真实触控设备，不再启用 `touch_emu`
- 触控状态机同时处理：
  - `ABS_MT_POSITION_X`
  - `ABS_MT_POSITION_Y`
  - `ABS_MT_TRACKING_ID`
  - `BTN_TOUCH / BTN_LEFT`
  - `SYN_REPORT`
- 当 `ABS_MT_TRACKING_ID < 0` 时强制判定释放
- LCKFB 下输入映射不再走“自动猜测”，固定成单一映射模式

对应代码位置：

- `src/little/buildroot-ext/package/lawrec/src/ui/lvgl_port/k230/lv_port_indev.c`
- `src/little/buildroot-ext/package/lawrec/src/ui/lvgl_port/k230/lv_port_disp.cpp`

### 3. 为什么之前会觉得是 touch_emu 在抢

这是一个典型误判点。

本轮板端实际执行：

- `ps | grep touch_emu`

返回里只有 `grep touch_emu` 本身，没有真正的 `touch_emu` 进程。

所以当前板端“鬼触”和“点击漂移”并不是 `touch_emu` 抢占，而是：

- `lawrec` 自己的 evdev 解析不完整
- 加上坐标映射策略不对，导致看起来像“触控不灵敏/误点/乱点”

本轮中文问题也不是源码编码错，而是 LVGL 内置 `lv_font_simsun_16_cjk` 的 glyph 集不包含当前菜单页全部汉字。

已经对照过当前 UI 页面实际汉字集合，缺失字符包括：

### 5. 本轮中文字库修法

为了不再依赖不完整的内置字体，本轮新增了 `lawrec` 自己的精简中文字库：

- 文件：
  - `src/little/buildroot-ext/package/lawrec/src/ui/src/lawrec_font_cn_16.c`

生成方式：

- 使用独立 `node` Docker 容器安装 `lv_font_conv`
- 使用 LVGL 自带的 `SimSun.woff`
- 只提取当前菜单页实际用到的汉字，加上 ASCII 范围

这样做的好处：

- 不污染主机环境
- 字库体积可控
- 页面上用到的汉字都能稳定显示

### 6. 本轮 little 镜像的正确生成方式

本轮再次确认，little 产物正确合成顺序必须是：

1. 从 `images/little-core/rootfs.cpio` 重新展开
2. 覆盖 `output/.../little/linux/rootfs/`
3. 覆盖 `output/.../little/buildroot-ext/target/`
4. 覆盖 `board/common/post_copy_rootfs/`
5. 重建 `rootfs.ext4`
6. 再生成 `sysimage-sdcard.img`

如果少了第 2 步，会出现：

- 新驱动 / 新 DTS / 新 rootfs 服务脚本之间不一致

如果少了第 3 步，会出现：

- 板上没有最新的 `lawrec ui`
- `ssh` 推送版能看到效果，但烧录镜像后又退回旧程序

### 7. 本轮最终应该重点复核什么

烧录本轮镜像后，优先看这几项：

- `dmesg | grep -i -E 'ft5|edt|touch'`
- `cat /proc/bus/input/devices`
- `cat /tmp/lawrec-ui.log`
- 开机是否还打印 `Generating ssh host keys`

预期：

- 触控设备为 `generic ft5x06 (8d)`，挂在 `event1`
- `lawrec-ui.log` 应显示：
  - `lawrec indev: abs x=[0,479] y=[0,799]`
  - `lawrec indev: use /dev/input/event1`
- 若镜像已真正更新，`sshd` 不应每次启动都重新生成 host keys
